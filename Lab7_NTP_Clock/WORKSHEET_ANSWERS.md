## คำถามระหว่างอ่านโค้ด

| ข้อ | เฉลย |
|---|---|
| 5.1 | (ก) `lastSyncAtMs` กับ `now` เป็น `millis()` ทั้งคู่ จึงลบกันได้ระยะเวลาที่ผ่านไป (`now − lastSyncAtMs`) โดยไม่ต้องรู้เวลาจริง และการลบแบบ `uint32_t` ยังถูกต้องแม้ `millis()` วนกลับ (ราว 49.7 วัน) (ข) `volatile` เพราะ callback (task เครือข่าย) เขียนค่า และ `loop()` (อีก task) อ่านค่า ถ้าไม่ใส่ คอมไพเลอร์อาจแคชค่าไว้ใน register แล้ว `loop()` มองไม่เห็นการเปลี่ยนแปลง |
| 5.2 | (ก) callback ทำงานใน task ของเครือข่าย ถ้าทำงานหนักหรือใช้ `Serial`/จอ (ซึ่ง `loop()` ก็ใช้อยู่ ไม่ปลอดภัยเมื่อสอง task ใช้พร้อมกัน) อาจหน่วงเครือข่ายหรือเกิดข้อมูลชนกัน จึงแค่ตั้งธงแล้วให้ `loop()` ทำต่อ (ข) `ntpStartedAt` คือเวลาที่เริ่มขอครั้งล่าสุด: ล้มเหลวที่ +20 วินาที แล้วขอใหม่เมื่อครบ +30 วินาทีจากการเริ่มขอ (คือ 10 วินาทีหลังล้มเหลว) และพิมพ์ `[NTP] requesting ...` (ค) **ไม่เปลี่ยน** เพราะ `updateNtp()` ย้อนกลับเป็น `Idle` เฉพาะเมื่อกำลัง `Syncing` อยู่เท่านั้น ถ้า `Synced` แล้ว ค่าเวลายังใช้ได้และนาฬิกายังเดินต่อ |
| 5.3 | (ก) `false` เพราะ `syncCount == 0` (เงื่อนไขเดียวก็เพียงพอในกรณีนี้ เพราะเวลาตอนเปิดเครื่องใกล้ปี 1970 ซึ่งต่ำกว่า `SANE_EPOCH` อยู่แล้ว) เหตุที่ใช้สองเงื่อนไข: ป้องกันสองชั้น และสื่อความหมายชัดว่า "เวลานี้ผ่านการ sync ในรอบการทำงานนี้แล้ว" ไม่ใช่เวลาที่มาจากแหล่งอื่น (ตอบตามเหตุผลที่สมเหตุสมผลได้) (ข) **2 ชั่วโมง** (`NTP_RESYNC_MS` 1 ชั่วโมง × `NTP_STALE_FACTOR` 2) |
| 5.4 | (ก) ตัวอย่าง `2026-10-09 19:55:54` (ตามวันที่ทดลอง) (ข) คืน `false` และข้อความ `NOT_SYNCED` |
| 5.5 | (ก) 1 วันมี 86,400 วินาที `t % 86400` คือจำนวนวินาทีนับจากเที่ยงคืน UTC ของวันนั้น ค่านี้เปลี่ยนทุกวินาที จึงใช้เช็คว่า "วินาทีเปลี่ยนหรือยัง" (ข) วาดใหม่ **วินาทีละ 1 ครั้ง** (ส่วนวาดจอถูกเรียกไม่ถี่เกินทุก `DISPLAY_REFRESH_MS` = 100 ms และวาดจริงเมื่อคีย์เปลี่ยนเท่านั้น) (ค) วาดวันที่ใหม่เมื่อวันท้องถิ่นเปลี่ยน (เที่ยงคืนเวลาไทย) ถ้าใช้ `t / 86400` ตรงๆ คีย์จะเปลี่ยนที่เที่ยงคืน **UTC = 07:00 น. เวลาไทย** วันที่บนจอจึงค้างเป็นของเมื่อวานช่วง 00:00–07:00 น. (โค้ดเดิมมีข้อผิดพลาดนี้ แก้แล้วในเวอร์ชันปัจจุบัน) |
| 5.6 | NotConfigured/Idle → **NO WIFI** (แดง); Connecting/Idle → **WIFI...** (น้ำเงิน); Connected/Syncing → **SYNCING** (น้ำเงิน); Connected/Synced เพิ่ง sync → **SYNCED** (เขียว); Connected/Failed → **NO SYNC** (แดง); Connected/Synced เก่า 3 ชั่วโมง → **STALE** (เหลือง) |
| 5.7 | (ก) โหมด Station: บอร์ดเป็น "ลูกข่าย" ที่ไปต่อกับเราเตอร์ (เหมือนมือถือต่อ WiFi) (ข) ลงทะเบียน callback ให้ไลบรารี SNTP เรียก `onTimeSync()` ทุกครั้งที่ได้เวลา |
| 5.8 | **ไม่ผิดพลาด** เพราะเวลาจริงมาจากนาฬิกาในตัวที่เดินต่อเอง และ callback ทำงานคนละ task กับ `loop()` การหยุดรอ ≈ 25.8 ms สั้นมาก ในตัวอย่างที่เก็บ (Serial) ไม่พบการอ่านพลาดหรือ sync ผิดปกติขณะอ่านเซนเซอร์ |

## แบบฝึกหัด

### ข้อ 1 — รูปแบบวันที่ และการคำนวณความกว้าง
เปลี่ยนรูปแบบวันที่ (ตำแหน่งในฟังก์ชัน `updateClockCard()`)
```cpp
formatLocalTime(text, sizeof(text), "%d/%m/%Y");    // เดิม "%a %d %b %Y"
```
(เปลี่ยนสตริง ไม่มีผลต่อการ build) ผลที่คาด: `09/10/2026`

**คำนวณ:** `07:49:08 PM` ที่ฟอนต์ 4: ตัวเลข 6 ตัว × 14 = 84, `:` 2 ตัว × 7 = 14, เว้นวรรค 5, `P` 16, `M` 21 รวม = **140 พิกเซล** ที่ขยาย 2 เท่า = **280 พิกเซล** เริ่มที่ x = 16 จบที่ x = 296 ซึ่งเกินตำแหน่งป้ายสถานะ (x = 220) จึง **ชน/ทับป้าย SYNCED** (พื้นที่ที่ใช้ได้ ≈ 204 พิกเซล: `19:49:08` กว้าง 196) ทางแก้: ลดขนาดตัวอักษร ย้ายป้าย หรือแสดง AM/PM ตัวเล็กแยก

### ข้อ 2 — เขตเวลา
```cpp
constexpr long GMT_OFFSET_SEC = 9 * 3600;
```
เวลาเปลี่ยน **+2 ชั่วโมง** (จาก UTC+7 เป็น UTC+9) ตอนแรกป้ายชื่อการ์ดยัง **เขียนว่า `TIME (UTC+7)` อยู่** เพราะ hard-code ไว้ใน `drawMainScreenStatic()` ทำให้ป้ายขัดกับเวลาที่แสดง วิธีแก้ (build ผ่านแล้ว)
```cpp
char clockLabel[24];
snprintf(clockLabel, sizeof(clockLabel), "TIME (UTC%+ld)", app::GMT_OFFSET_SEC / 3600);
drawCard(CLOCK_CARD_X, CLOCK_CARD_Y, CLOCK_CARD_W, CLOCK_CARD_H, clockLabel);
```
ผลที่คาด: `TIME (UTC+9)` ที่ 9 ชั่วโมง และ `TIME (UTC+7)` เมื่อคืนค่า (ผลบนบอร์ดยังไม่ได้ทดสอบ) สังเกต: Serial มีข้อความ `(UTC+…)` ที่คำนวณจาก `GMT_OFFSET_SEC` อยู่แล้ว

### ข้อ 3 — คำนวณ epoch
(ก) 1,760,000,000 ÷ 86,400 = 20,370 วัน เศษ 32,000 วินาที = 08:53:20 วันที่ 20,370 นับจาก 1 ม.ค. 1970 = **2025-10-09** → **2025-10-09 08:53:20 UTC** และ **15:53:20 UTC+7** (ตรวจด้วยสคริปต์แล้ว)
(ข) 19:49:08 − 7 ชั่วโมง = **12:49:08 UTC**
(ค) 7 × 3600 = **25,200 วินาที**
(ง) (3,900,000 − 600,000) ms = 3,300,000 ms = 3,300 s = **55 นาที**

### ข้อ 4 — ขอเวลาไม่สำเร็จ
```cpp

inline constexpr char NTP_SERVER_2[] = "no-such-ntp2.invalid";

```
(**ตรวจจากบอร์ดจริงแล้ว** ผลดังนี้) ลำดับใน Serial: `[NTP] requesting time from no-such-ntp.invalid / ...` → `[TIME] NOT SYNCED (wifi=CONNECTED ntp=SYNCING)` → `[NTP] no reply within 8 s (UDP port 123 blocked? DNS problem?) - will retry` → `ntp=FAILED` → ขอใหม่ (วนซ้ำ) ไม่มีการแสดงเวลาปี 1970 ป้ายบนจอที่คาด: `SYNCING` (น้ำเงิน) ↔ `NO SYNC` (แดง) (**ยังไม่ได้ดูบนจอ**) ที่ค่าเริ่มต้น (20/30 วินาที) ล้มเหลวที่ +20 s แล้วขอใหม่ที่ +30 s

## ข้อควรระวังและข้อสังเกตสำหรับผู้สอน

1. **เครือข่ายที่บล็อก UDP 123:** ต่อ WiFi ได้แต่ sync ไม่ได้ (ป้าย `NO SYNC`) ควรทดสอบเครือข่ายของโรงเรียนก่อนสอน และเตรียม hotspot มือถือสำรอง
2. **ความเป็นส่วนตัวของ WiFi:** อย่าให้นักเรียนส่ง `secrets.h` และตรวจภาพ/log ก่อนรับ โปรแกรมนี้ไม่พิมพ์ชื่อ WiFi ลง Serial
3. **เรื่องข้อบกพร่องของคีย์วันที่ (UTC เทียบกับเวลาท้องถิ่น)** เป็นตัวอย่างที่ดีของข้อผิดพลาดที่เกิดจากการลืมเขตเวลา ใช้เป็นหัวข้ออภิปรายคำถาม 5.5 (ค) ได้
4. **รอบ sync ของไลบรารีไม่เท่ากับค่าที่ตั้งเป๊ะ** (ตัวอย่าง 30 → 30 s แล้ว 45 s) ถ้านักเรียนทำข้อ 5 อาจเห็น STALE ชั่วคราว ให้ตรวจเหตุผลมากกว่าตัวเลข
5. **เรื่อง drift (การคลาดเคลื่อน):** ผู้เขียนยังไม่ได้วัด ถ้าสนใจ ให้นักเรียนวัดเอง (ที่ความละเอียดวินาที การเทียบระยะสั้นๆ จะเห็นความต่างยาก ต้องรอหลายชั่วโมง)
6. **ข้อ 4 ข้อ 5:** ปรับ timeout/retry ให้สั้นลงเพื่อไม่ต้องรอนาน แต่ต้องคืนค่าเดิมก่อนส่งงาน
