# Level 1 / Lab 11 — MQTT Farm: ส่งข้อมูลและรับคำสั่งผ่านอินเทอร์เน็ต

Lab นี้ต่อยอดจาก Lab 10 (Smart Farm Controller) โดยเพิ่ม **MQTT**: บอร์ดส่งค่าเซนเซอร์และสถานะขึ้น broker (ค่าเริ่มต้นคือ broker สาธารณะ `broker.hivemq.com` ไม่ต้องมี user/password)
แล้วดูได้จากคอมพิวเตอร์หรือมือถือ และสั่งพัดลม/ไฟปลูก/ปั๊มกลับมาทาง MQTT ได้ (เปิดรับคำสั่งเฉพาะเมื่อกดปุ่มบนจอ)

> **สถานะการตรวจสอบ (อ่านก่อน):** โปรแกรมนี้ build ผ่านไม่มี warning และทดสอบบนบอร์ดจริงกับ broker จริงแล้ว ผู้พัฒนาตรวจจอ 4 แท็บ (SETUP, DASH, MQTT, SYS) และใช้ **MQTT Explorer** ดูค่า `telemetry` สดๆ
> แล้วยืนยันว่าใช้งานได้ถูกต้อง (มีภาพถ่าย) ผมทดสอบเพิ่มจากฝั่งคอมพิวเตอร์ด้วยโปรแกรมเล็กๆ ที่ subscribe topic ของบอร์ดและส่งคำสั่ง: ทุกคำสั่งทำงาน/ถูกปฏิเสธตามที่ออกแบบ, ข้อความ Last Will (`offline`) ทำงาน,
> และวัดเวลาที่โปรแกรมหยุดรอเมื่อเชื่อมต่อ broker ไม่ได้
> **ที่ยังไม่ได้ยืนยัน:** การส่งคำสั่งจาก MQTT Explorer (ในภาพมีหน้าส่งคำสั่งเตรียมไว้แต่ผมไม่เห็นผลลัพธ์), ภาพปุ่ม `REMOTE ON` สีส้มกับวงแหวนที่แถบหัว, หน้า CTRL ของ Lab นี้ (ไม่มีภาพ), การรับมือ WiFi หลุดและ broker ล่ม**หลังเชื่อมต่อแล้ว**,
> การเข้ารหัส/รหัสผ่าน (Lab นี้ไม่ใช้) ดูตาราง "สถานะการตรวจสอบ" ท้ายไฟล์ ภาพ ASCII วาดประกอบ
>
> **ความปลอดภัย:** broker สาธารณะ **ใครก็อ่านและส่งข้อความเข้า topic ได้** ใช้เพื่อเรียนรู้แนวทางเท่านั้น อย่าส่งข้อมูลส่วนตัว และอย่านำไปควบคุมของจริง (ของจริงต้องใช้ broker ที่มี user/password และ TLS)

## สิ่งที่จะได้เรียน

1. **MQTT แบบ publish/subscribe:** อุปกรณ์ไม่ต้องรู้ IP ของกันและกัน คุยผ่านคนกลาง (broker) ด้วย **topic** แบบลำดับชั้น (`cydfarm/5bad34/telemetry`)
2. **ออกแบบ topic และ payload (JSON)** สำหรับข้อมูลสถานะ เหตุการณ์ คำสั่ง และการตอบกลับ
3. **retained message** (ผู้ที่เพิ่ง subscribe เห็นค่าล่าสุดทันที) และ **Last Will (LWT)** (broker ประกาศ `offline` แทนเมื่อบอร์ดหลุด)
4. **client id ต้องไม่ซ้ำ** (ซ้ำ = broker ตัดอีกฝั่ง) และ **keep-alive**
5. **ความปลอดภัยของคำสั่งทางเครือข่าย:** ปิดไว้เป็นค่าเริ่มต้น เปิดแล้วหมดอายุเอง, ไม่เชื่อข้อมูลจากภายนอก (ตรวจและกรองก่อนใช้), ตอบผลกลับ (ack), ปั๊มยังติด watchdog/cooldown
6. **เครือข่ายต้องไม่ขัดจังหวะตัวควบคุม:** การเชื่อมต่อใช้เวลา จึงใช้ timeout สั้น ลองใหม่แบบห่างขึ้นเรื่อยๆ (exponential backoff) และวัดเวลาที่โปรแกรมหยุดรอ
7. ใช้เครื่องมือ MQTT (MQTT Explorer หรือ HiveMQ Web Client) ดูและสั่งงานระบบจริง

## สรุป topic (root = `cydfarm/<รหัส 6 หลักจาก MAC>` ของบอร์ดต้นแบบคือ `cydfarm/5bad34`)

รหัสของบอร์ดคุณดูได้จาก Serial (`[MQTT] root topic: …`) หรือหน้า MQTT บนจอ

### บอร์ดส่งออก (ให้ subscribe)

| topic | ส่งเมื่อ | retained | ตัวอย่าง |
|---|---|---|---|
| `<root>/telemetry` | ทุก 10 วินาที (และทันทีหลังเชื่อมต่อ) | ใช่ | JSON ค่าเซนเซอร์และสถานะ (ดูด้านล่าง) |
| `<root>/status` | ตอนเชื่อมต่อ และเมื่อหลุด (LWT) | ใช่ | `online` / `offline` |
| `<root>/event` | ปั๊ม/พัดลม/ไฟเปลี่ยนสถานะ, เปลี่ยนโหมด, estop, เปิด-ปิด remote | ไม่ | `{"event":"pump_on","detail":"SOIL DRY","ts":"…","uptime_s":125}` |
| `<root>/ack` | หลังรับคำสั่งทุกครั้ง | ไม่ | `{"cmd":"pump","payload":"ON","result":"accepted"}` |

subscribe ทีเดียวทั้งหมดด้วย `<root>/#`

ตัวอย่าง `telemetry` จริงจากบอร์ดต้นแบบ (250 ไบต์):

```json
{"ts":"2026-10-09 22:33:09","uptime_s":63,"temp":33.8,"hum":70,"light":0,"soil":48,"src":"REAL",
 "fan":{"duty":76,"mode":"AUTO","failsafe":false},"lamp":{"on":false,"mode":"AUTO"},
 "pump":{"on":false,"mode":"AUTO","rest_s":0},"remote":false,"rssi":-56}
```

| ฟิลด์ | ความหมาย |
|---|---|
| `ts`, `uptime_s` | เวลาท้องถิ่น (`NOT_SYNCED` ถ้ายังไม่ได้เวลาจริง) และวินาทีตั้งแต่เปิดเครื่อง |
| `temp` (°C), `hum` (%), `light` (%), `soil` (%) | ค่าเซนเซอร์ (`null` ถ้ายังไม่มีค่า, `soil` เป็นค่าจำลอง) |
| `src` | `REAL`, `SIM-RANDOM`, `SIM-SWEEP` หรือ `NONE` (แหล่งของอุณหภูมิ/ความชื้น) |
| `fan` | `duty` 0–100, `mode`, `failsafe` |
| `lamp` | ไฟปลูก: `on`, `mode` |
| `pump` | `on`, `mode`, `rest_s` = วินาทีที่ยังต้องพัก |
| `remote` | `true` = กำลังรับคำสั่งทาง MQTT |
| `rssi` | ความแรงสัญญาณ WiFi (dBm) |

ข้อสังเกต: telemetry ตัวแรกหลังเชื่อมต่อ (ที่ uptime ≈ 3 วินาที) อาจมี `temp`/`hum` เป็น `null` และ `src` เป็น `NONE` เพราะ DHT11 ยังไม่ได้อ่านครั้งแรก (วัดจากบอร์ดต้นแบบ) และเพราะ retained ผู้ที่ subscribe ตอนนั้นจะเห็นค่านี้จนกว่าจะมีข้อความใหม่ใน 10 วินาที

### บอร์ดรับเข้า (ให้ publish)

| topic | payload | ผล |
|---|---|---|
| `<root>/cmd/fan` | `ON` / `OFF` / `AUTO` | MANUAL ON (100%) / MANUAL OFF / กลับ AUTO |
| `<root>/cmd/light` | `ON` / `OFF` / `AUTO` | ไฟปลูก |
| `<root>/cmd/pump` | `ON` / `OFF` / `AUTO` | ปั๊ม (ติด watchdog 30 วินาทีและพัก 20 วินาที) |
| `<root>/cmd/estop` | อะไรก็ได้ | หยุดฉุกเฉิน: ทุกอุปกรณ์ MANUAL + OFF |

payload ไม่สนตัวพิมพ์เล็ก-ใหญ่ (`on` = `ON`) ส่วนชื่อคำสั่งต้องเป็นตัวพิมพ์เล็กตามตาราง
**คำสั่งทุกตัวถูกปฏิเสธจนกว่าจะเปิด `REMOTE`** (ปุ่มในแท็บ MQTT หรือพิมพ์ `r` ใน Serial) ซึ่งหมดอายุเองใน 10 นาที และปิดทุกครั้งที่เปิดเครื่อง

ผลที่เป็นไปได้ใน `ack.result`: `accepted`, `rejected: REMOTE is OFF`, `rejected: use ON/OFF/AUTO`, `rejected: unknown command`, `refused: pump resting N s`, `accepted: all MANUAL OFF`

## วิธีทดสอบ

1. อัปโหลด แล้ว calibrate จอสัมผัสครั้งแรก ดูแท็บ `MQTT` ว่า `STATE` เป็น `CONNECTED` และจุดที่แถบหัวเป็นสีเขียว
2. ใช้ **MQTT Explorer** (โปรแกรมฟรีบนคอมพิวเตอร์) หรือ **HiveMQ Web Client** (บนเว็บเบราว์เซอร์) เชื่อมต่อ `broker.hivemq.com` พอร์ต `1883` ไม่ต้องใส่ user/password
3. subscribe `<root>/#` ดูค่า telemetry ที่เปลี่ยนทุก 10 วินาที
4. แตะการ์ด `SOIL` บนหน้า DASH (ดินแห้ง) ดูข้อความ `event` ของปั๊มเริ่ม/หยุด
5. ลองส่ง `ON` ไปที่ `<root>/cmd/pump` ตอน REMOTE ปิด ต้องได้ `rejected: REMOTE is OFF` ใน `ack`
6. แตะ `REMOTE` บนจอ แล้วส่งคำสั่งซ้ำ ต้องได้ `accepted` และเห็นอุปกรณ์/LED เปลี่ยน

## หน้าจอ

เหมือน Lab 10 แต่แถบแท็บเป็น **5 ปุ่ม** (`DASH CTRL SETUP MQTT SYS`) และมีสิ่งใหม่

### แท็บ MQTT

```
┌──────────────────────────────────────┐
│ Lab 11 - MQTT Farm   ●  ●   06:18:32 │ ← ● ซ้าย = สถานะ MQTT (เขียว = เชื่อมต่อ)
│ BROKER   broker.hivemq.com:1883      │
│ STATE    CONNECTED                   │
│ TOPIC    cydfarm/5bad34              │
│ TRAFFIC  TX 3213  RX 0  drop 1       │ ← ข้อความที่ส่ง / รับ / ส่งไม่ได้
│ BLOCKED  last 610 ms, max 610 ms     │ ← เวลาที่โปรแกรมหยุดรอตอนเชื่อมต่อ
│ LAST CMD (none yet)                  │ ← คำสั่งล่าสุดและผล
│ ┌──────────────────────────────────┐ │
│ │   REMOTE OFF  (tap to allow)     │ │ ← แตะ = รับคำสั่งทาง MQTT 10 นาที
│ └──────────────────────────────────┘ │
│ [DASH][CTRL][SETUP][MQTT][ SYS ]     │
└──────────────────────────────────────┘
```

- `STATE`: `CONNECTED` (เขียว) / `RETRY Ns (rc=…)` (ส้ม) / `CONNECTING...` (น้ำเงิน) / `NO WIFI` (แดง)
- `TRAFFIC`: `TX` จำนวนข้อความที่ส่งออกสำเร็จ, `RX` คำสั่งที่รับ, `drop` เหตุการณ์ที่ส่งไม่ได้เพราะยังไม่เชื่อมต่อ (ไม่เก็บคิว)
- `BLOCKED`: เวลาที่ `mqtt.connect()` ทำให้โปรแกรมหยุดรอ (ครั้งล่าสุดและนานสุดตั้งแต่เปิดเครื่อง)
- `REMOTE`: เมื่อเปิดอยู่ปุ่มเป็นสีส้มพร้อมเวลานับถอยหลัง (เช่น `REMOTE ON 9:45 (tap = OFF)`) และมีวงแหวนสีส้มรอบจุดสถานะที่แถบหัว

### Serial

เพิ่มคำสั่ง `r` (เปิด/ปิด REMOTE) และ `m` (พิมพ์สถานะ MQTT) ส่วนคำสั่งเดิมของ Lab 10 ใช้ได้ทั้งหมด บรรทัดที่เพิ่ม:


## ความรู้ใหม่ใน Lab นี้

### MQTT พื้นฐาน

| คำ | ความหมาย |
|---|---|
| broker | เซิร์ฟเวอร์กลางที่รับข้อความและส่งต่อให้ผู้ที่ subscribe |
| topic | "ที่อยู่" ของข้อความ แบ่งชั้นด้วย `/` เช่น `cydfarm/5bad34/cmd/pump` |
| publish / subscribe | ส่งข้อความเข้า topic / ขอรับข้อความจาก topic |
| wildcard (ตอน subscribe) | `+` = แทนหนึ่งระดับ (`cydfarm/+/telemetry`), `#` = แทนทุกระดับที่เหลือ (ต้องอยู่ท้ายสุด `cydfarm/5bad34/#`) |
| QoS | ระดับการรับประกัน 0 = ส่งครั้งเดียว ไม่รับประกัน (Lab นี้ใช้ 0), 1 = อย่างน้อยหนึ่งครั้ง, 2 = ครั้งเดียวพอดี |
| retained | broker เก็บข้อความล่าสุดของ topic ไว้ส่งให้ผู้ที่ subscribe ทีหลัง (`status`, `telemetry`) |
| Last Will (LWT) | ข้อความที่ฝากไว้กับ broker ให้ประกาศแทนเมื่อบอร์ดหลุดโดยไม่ได้บอกลา (`status = offline`) |
| keep-alive | ส่ง ping ทุก 30 วินาที ถ้า broker ไม่ได้ยินนานเกินไปถือว่าหลุด |
| client id | ชื่อของบอร์ดบน broker ต้อง **ไม่ซ้ำกัน** ถ้าซ้ำ broker จะตัดการเชื่อมต่อของอีกฝั่ง (ที่นี่ใช้ `cydfarm-<รหัสจาก MAC>`) |

ผลที่วัดบนบอร์ดต้นแบบ: เชื่อมต่อ broker ใช้ 542–636 ms; ส่งคำสั่งจากคอมพิวเตอร์จนได้ `ack` กลับมา ≈ 0.4–0.6 วินาที (ครั้งหนึ่งช้าที่ 1.9 วินาที); หลังรีเซ็ตบอร์ด broker ประกาศ `status: offline` ตามด้วย `online` เมื่อเชื่อมต่อใหม่

### ปริมาณข้อมูล

telemetry หนึ่งข้อความ = payload 250 ไบต์ + topic 24 ไบต์ + ส่วนหัว ≈ 279 ไบต์ ทุก 10 วินาที ≈ 100 KB ต่อชั่วโมง ≈ 2.3 MB ต่อวัน (ยังไม่รวม ping และ event) ไลบรารี PubSubClient มีบัฟเฟอร์เริ่มต้น 256 ไบต์ ซึ่งเล็กกว่า 279 ไบต์ จึงต้องเรียก `mqtt.setBufferSize(512)` ไม่งั้นการ publish จะล้มเหลว (ทดสอบแล้วบนบอร์ด: เมื่อปิดบรรทัดนี้ telemetry ส่งไม่ออก Serial ขึ้น `publish to telemetry failed` ทุกครั้ง)

### เครือข่ายต้องไม่ขัดจังหวะตัวควบคุม

`mqtt.connect()` เป็นฟังก์ชันที่ **หยุดรอ** จนกว่าจะเชื่อมต่อสำเร็จหรือ timeout ถ้า broker ไม่ตอบ ตัวควบคุมทั้งหมด (จอสัมผัส, ปั๊ม, watchdog) จะค้างตลอดช่วงนั้น วัดจากบอร์ดต้นแบบ:

| กรณี | เวลาที่หยุดรอต่อครั้ง |
|---|---|
| broker ปกติ | 542–636 ms |
| IP ที่ไม่มีเครื่องอยู่ (ค่าเริ่มต้นของ `WiFiClient` รอ 3 วินาที) | **3.0 วินาที** |
| ตั้ง `MQTT_SOCKET_TIMEOUT_S = 2` (ค่าในโปรแกรมนี้) | **2.0 วินาที** |
| ชื่อ broker ที่ DNS หาไม่เจอ | 15–30 ms (ล้มเหลวทันที) |

โปรแกรมจึงลองเชื่อมต่อใหม่แบบ **exponential backoff**: รอ 5 → 10 → 20 → 40 → 60 วินาที (สูงสุด 60) เพื่อไม่ให้ค้างบ่อย ตัวเลขนี้แสดงในหน้า MQTT (`BLOCKED`) การค้างสูงสุด ≈ 2 วินาทียังต่ำกว่า watchdog ปั๊ม 30 วินาที แต่จอสัมผัสจะไม่ตอบสนองในช่วงนั้น ซึ่งเป็นข้อจำกัดของโปรแกรมเธรดเดียว (ทางแก้ที่เหมาะกว่า คือแยกงานเครือข่ายไปอีก task ของ FreeRTOS ซึ่งไม่ได้ทำใน Lab นี้)

| มาตรการ | เหตุผล |

## ค่าที่ปรับได้ใน `app_config.h`

| ค่า | ความหมาย |
|---|---|
| `MQTT_HOST`, `MQTT_PORT` | broker (ค่าเริ่มต้น `broker.hivemq.com`, 1883) |
| `MQTT_TOPIC_PREFIX` | ต้นของ topic (ค่าเริ่มต้น `cydfarm`) ต่อท้ายด้วยรหัสจาก MAC อัตโนมัติ |
| `MQTT_TELEMETRY_MS` | ส่ง telemetry ทุกกี่ ms (10000) |
| `MQTT_RECONNECT_MIN_MS`, `MQTT_RECONNECT_MAX_MS` | backoff 5 วินาที → สูงสุด 60 วินาที |
| `MQTT_SOCKET_TIMEOUT_S` | รอ broker/การเชื่อมต่อนานสุดกี่วินาที (2) |
| `MQTT_KEEPALIVE_S` | ping ทุกกี่วินาที (30) |
| `REMOTE_ENABLE_MS` | เปิดรับคำสั่งได้นานกี่ ms (600000 = 10 นาที) |
| ค่าที่เหลือ | เหมือน Lab 10 (เกณฑ์ ตารางเวลา ปั๊ม LDR จอสัมผัส) |

## สถานะการตรวจสอบ

| รายการ | สถานะ | หลักฐาน |
|---|---|---|
| build ผ่าน ไม่มี warning ในโค้ดของเรา | **ยืนยันแล้ว** | RAM 14.6%, Flash 64.8% (ไลบรารี PubSubClient 2.8.0) |
| เชื่อมต่อ broker สาธารณะ, ส่ง `status`/`telemetry` (retained), `event`, `ack` | **ยืนยันแล้ว** | ผมรับจากฝั่งคอมพิวเตอร์ครบทุก topic ; ผู้พัฒนาเห็น telemetry สดใน MQTT Explorer (ภาพ) |
| หน้า MQTT แสดงสถานะถูกต้อง | **ยืนยันแล้วจากภาพ** | `CONNECTED`, topic, `TX 3213 RX 0 drop 1`, `last 610 ms, max 610 ms`, ปุ่ม `REMOTE OFF` |
| แท็บ 5 ปุ่ม และหน้า SETUP / DASH / SYS (เลย์เอาต์) | **ยืนยันแล้วจากภาพ** | ข้อความพอดีไม่ชน ; บรรทัดเล็กล่างสุดของหน้า SYS ในภาพถูกตัดท้าย ผมแก้ให้สั้นลงแล้ว (ยังไม่มีภาพหลังแก้) |
| ใช้งานต่อเนื่อง | **ยืนยันบางส่วน** | จากภาพ: `uptime_s` ≈ 27,883 (≈ 7 ชม. 45 นาที) ยังเชื่อมต่ออยู่ ส่งแล้ว 3,213 ข้อความ ; ไม่ได้ทดสอบเกินนี้ |
| คำสั่งทางเครือข่ายเมื่อ REMOTE เปิด/ปิด | **ยืนยันแล้ว** | ผมส่งจากคอมพิวเตอร์: ปิด = `rejected: REMOTE is OFF` ทุกคำสั่ง ; เปิดแล้ว `fan/light/pump` ON/OFF/AUTO และ `estop` ได้ `accepted` อุปกรณ์เปลี่ยนจริง (Serial) |
| ปั๊มปฏิเสธคำสั่งระหว่างพัก ; payload ผิด ; คำสั่งไม่รู้จัก | **ยืนยันแล้ว** | `refused: pump resting 16 s`, `rejected: use ON/OFF/AUTO`, `rejected: unknown command` |
| REMOTE หมดอายุเองใน 10 นาที | **ยังไม่ได้ยืนยัน** | โค้ดตรวจเวลาแล้วแต่ยังไม่ได้รอครบ 10 นาที (ควรทดสอบโดยลด `REMOTE_ENABLE_MS`) |
| Last Will: `offline` เมื่อบอร์ดหลุด | **ยืนยันแล้ว** | รีเซ็ตบอร์ดขณะ subscribe : ได้ `status: offline` แล้ว `status: online` เมื่อเชื่อมต่อใหม่ ; ยังไม่ได้ทดสอบกรณีดึง WiFi/ปลั๊กออก |
| เวลาที่โปรแกรมหยุดรอเมื่อเชื่อมต่อไม่ได้ | **วัดจริงแล้ว** | IP ที่ไม่ตอบ 3.0 → 2.0 วินาที (หลังตั้ง timeout), DNS ล้มเหลว 15–30 ms, backoff 5/10/20 วินาที (ตามบันทึก) |
| เชื่อมต่อใหม่เมื่อ WiFi หลุดหรือ broker ล่ม **หลังเชื่อมต่อแล้ว** | **ยังไม่ได้ทดสอบ** | โค้ดมีเส้นทางนี้แต่ยังไม่เคยถูกกระตุ้น (ทดสอบแต่กรณีเชื่อมต่อไม่ได้ตั้งแต่เริ่ม) |
| ปุ่ม `REMOTE ON` สีส้มและวงแหวนที่แถบหัว | **ยืนยันบางส่วน** | Serial ยืนยันว่าแตะเปิดได้ (`remote commands ENABLED`) ; ยังไม่มีภาพ |
| ส่งคำสั่งจาก MQTT Explorer | **ยังไม่ได้ยืนยัน** | ภาพมีหน้า Publish ที่เตรียม `cmd/pump` = `OFF` แต่ไม่เห็นผล ; การส่งจากโปรแกรมของผมยืนยันแล้ว |
| หน้า CTRL ใน Lab นี้ | **ยังไม่มีภาพ** | โค้ดส่วนนี้เหมือน Lab 10 |
| QoS 1/2, TLS, user/password | **ไม่ได้ใช้/ทดสอบ** | Lab นี้ใช้ QoS 0 บน broker สาธารณะ |
| ภาพ ASCII ใน README | วาดประกอบ | ไม่ใช่ผลจริง |
