## 1. เป้าหมายการเรียนรู้

เมื่อจบใบงานนี้ ผู้เรียนต้องทำได้ทุกข้อ

1. อธิบายหลักการ **publish/subscribe** ผ่าน broker เทียบกับการเชื่อมต่อตรง (เช่น เว็บเซิร์ฟเวอร์บนบอร์ด) และบอกข้อดี-ข้อเสีย
2. อ่านและออกแบบ **topic แบบลำดับชั้น** และบอกได้ว่า wildcard `+` กับ `#` แทนอะไร
3. อธิบาย **retained message**, **Last Will (LWT)**, **keep-alive**, **QoS 0/1/2** และ **client id ที่ต้องไม่ซ้ำ**
4. อ่าน payload แบบ **JSON** และคำนวณขนาดข้อความ/ปริมาณข้อมูลต่อชั่วโมง
5. ใช้ MQTT client ดูค่า สั่งงาน และอ่านผลตอบกลับ (`ack`) ของระบบจริง
6. อธิบายมาตรการความปลอดภัยของคำสั่งทางเครือข่าย: ปิดเป็นค่าเริ่มต้น หมดอายุเอง กรองข้อมูลจากภายนอก ยังติดข้อจำกัดของอุปกรณ์ และบอกข้อจำกัดของ broker สาธารณะ
7. อธิบายได้ว่าทำไมการเชื่อมต่อเครือข่ายที่ "หยุดรอ" จึงเป็นอันตรายต่อตัวควบคุม และคำนวณผลของ **exponential backoff**
8. ดัดแปลงโปรแกรมเพิ่มข้อมูลใน telemetry, คำสั่งตัวเลข และ topic สถานะแบบ retained พร้อมทดสอบด้วย MQTT client

## 3. ความรู้พื้นฐานที่ต้องเข้าใจก่อนลงมือ

### 3.1 MQTT คืออะไร

MQTT เป็นโปรโตคอลส่งข้อความขนาดเล็กสำหรับอุปกรณ์ IoT แบบ **publish/subscribe** ผ่านคนกลางที่เรียกว่า **broker**

| | เชื่อมต่อตรง (เช่น เว็บเซิร์ฟเวอร์บนบอร์ด) | MQTT ผ่าน broker |
|---|---|---|
| ผู้ติดต่อต้องรู้ | IP/พอร์ตของบอร์ด (อยู่ในเครือข่ายเดียวกัน หรือเปิดพอร์ตผ่านเราเตอร์) | แค่ชื่อ broker และ topic |
| บอร์ดหลังเราเตอร์/NAT | ต่อจากภายนอกยาก | บอร์ดต่อออกไปหา broker เอง จึงผ่านได้ |
| ผู้ดูหลายคน | บอร์ดต้องรับทุกคน | broker กระจายให้ |
| บอร์ดออฟไลน์ | ติดต่อไม่ได้ ไม่รู้สาเหตุ | ฝาก Last Will ให้ broker ประกาศได้ |
| ข้อเสีย | ตั้งค่าเครือข่ายซับซ้อน | พึ่ง broker (ล่ม/ดักอ่านได้ถ้าไม่เข้ารหัส) |

แต่ละอุปกรณ์เชื่อมต่อกับ broker (TCP พอร์ต 1883 แบบไม่เข้ารหัส, 8883 แบบ TLS) แล้ว **publish** ข้อความเข้า topic หรือ **subscribe** เพื่อรับข้อความจาก topic

### 3.2 topic และ wildcard

topic เป็นสายอักขระแบ่งชั้นด้วย `/` ตัวอย่างของ Lab นี้ (root = `cydfarm/5bad34`):

```
cydfarm/5bad34/telemetry        cydfarm/5bad34/cmd/pump
cydfarm/5bad34/status           cydfarm/5bad34/cmd/estop
cydfarm/5bad34/event            cydfarm/5bad34/ack
```

ตอน **subscribe** ใช้ wildcard ได้ (ตอน publish ห้ามใช้):

| wildcard | ความหมาย | ตัวอย่าง |
|---|---|---|
| `+` | แทน **หนึ่งระดับ** | `cydfarm/+/telemetry` ตรงกับ `cydfarm/5bad34/telemetry` และ `cydfarm/aaaaaa/telemetry` |
| `#` | แทน **ทุกระดับที่เหลือ** (ต้องอยู่ท้ายสุด) | `cydfarm/5bad34/#` ตรงกับทั้ง `telemetry`, `status`, `cmd/pump`, … |

### 3.3 root topic และ client id จาก MAC

บน broker สาธารณะมีคนใช้พร้อมกันมาก ชื่อ topic และ client id **ต้องไม่ซ้ำกับใคร** โปรแกรมสร้างจาก MAC address ของบอร์ด (3 ไบต์ท้าย):

```cpp
uint8_t mac[6];
esp_read_mac(mac, ESP_MAC_WIFI_STA);
snprintf(mqttRoot, sizeof(mqttRoot), "%s/%02x%02x%02x", "cydfarm", mac[3], mac[4], mac[5]);   // cydfarm/5bad34
snprintf(mqttClientId, sizeof(mqttClientId), "cydfarm-%02x%02x%02x", mac[3], mac[4], mac[5]);  // cydfarm-5bad34
```

ถ้ามีสองอุปกรณ์ใช้ client id เดียวกัน broker จะตัดการเชื่อมต่อของอุปกรณ์เดิมทิ้ง (วนตัดกันไปมา) ส่วนชื่อ topic ที่ "เดายาก" **ไม่ใช่ความปลอดภัย** ใครรู้ชื่อก็เข้าถึงได้

### 3.4 topic ของ Lab นี้

**บอร์ดส่งออก (publish):**

| topic | ส่งเมื่อ | retained |
|---|---|---|
| `<root>/telemetry` | ทุก 10 วินาที (และทันทีหลังเชื่อมต่อ) | ใช่ |
| `<root>/status` | ตอนเชื่อมต่อ (`online`) และเมื่อหลุด (`offline` โดย LWT) | ใช่ |
| `<root>/event` | ปั๊ม/พัดลม/ไฟเปลี่ยน, เปลี่ยนโหมด, estop, เปิด-ปิด remote | ไม่ |
| `<root>/ack` | หลังรับคำสั่งทุกครั้ง | ไม่ |

**บอร์ดรับเข้า (subscribe `<root>/cmd/#`):**

| topic | payload | ผล |
|---|---|---|
| `<root>/cmd/fan` | `ON` / `OFF` / `AUTO` | MANUAL ON (100%) / MANUAL OFF / กลับ AUTO |
| `<root>/cmd/light` | `ON` / `OFF` / `AUTO` | ไฟปลูก |
| `<root>/cmd/pump` | `ON` / `OFF` / `AUTO` | ปั๊ม (ยังติด watchdog 30 วินาทีและพัก 20 วินาที) |
| `<root>/cmd/estop` | อะไรก็ได้ | ทุกอุปกรณ์ MANUAL + OFF |

### 3.5 payload แบบ JSON และขนาดข้อความ

telemetry เป็นข้อความ JSON (ตัวอย่างจริง 250 ไบต์):

```json
{"ts":"2026-10-09 22:33:09","uptime_s":63,"temp":33.8,"hum":70,"light":0,"soil":48,"src":"REAL",
 "fan":{"duty":76,"mode":"AUTO","failsafe":false},"lamp":{"on":false,"mode":"AUTO"},
 "pump":{"on":false,"mode":"AUTO","rest_s":0},"remote":false,"rssi":-56}
```

ฟิลด์ที่ไม่มีค่าเป็น `null` (เช่นก่อน DHT11 อ่านครั้งแรก) โปรแกรมสร้าง JSON ด้วย `snprintf` ลงบัฟเฟอร์ แล้วตรวจค่าที่ `snprintf` คืน: ถ้า ≥ ขนาดบัฟเฟอร์แปลว่าข้อความถูกตัด จะไม่ส่ง

ขนาดแพ็กเก็ต MQTT (QoS 0) ≈ ส่วนหัว 1 ไบต์ + ความยาวที่เหลือ 2 ไบต์ + ความยาว topic 2 ไบต์ + topic + payload:
`1 + 2 + 2 + 24 + 250 = 279` ไบต์ ซึ่ง **ใหญ่กว่าบัฟเฟอร์เริ่มต้น 256 ไบต์ของ PubSubClient** จึงต้องเรียก `mqtt.setBufferSize(512)` (ถ้าไม่เรียก การ publish จะล้มเหลว ทดสอบแล้วบนบอร์ด)

ปริมาณข้อมูล: 279 ไบต์ × 6 ข้อความต่อนาที × 60 = **100,440 ไบต์ ≈ 98 KB ต่อชั่วโมง** ≈ 2.3 MB ต่อวัน

### 3.6 retained, Last Will, keep-alive, QoS

- **retained:** broker เก็บ "ข้อความล่าสุด" ของ topic ไว้ ผู้ที่ subscribe ทีหลังเห็นทันที ใช้กับสถานะ (`status`, `telemetry`) ไม่ใช้กับเหตุการณ์ (`event`, `ack`) เพราะคนที่มาทีหลังจะเห็นเหตุการณ์ "เก่า" เหมือนเพิ่งเกิด
  ข้อควรระวัง: ข้อความ retained ค้างบน broker จนกว่าจะถูกเขียนทับหรือลบ (ส่ง payload ว่างแบบ retained)
- **Last Will (LWT):** ตอนเชื่อมต่อ บอร์ดฝากข้อความไว้กับ broker (`status = offline`, retained) ถ้าบอร์ดหลุดโดยไม่ได้ปิดการเชื่อมต่ออย่างเรียบร้อย broker จะเป็นฝ่ายประกาศให้ ส่วนเมื่อต่อสำเร็จบอร์ดประกาศ `online` เอง

```cpp
mqtt.connect(clientId, nullptr, nullptr, "cydfarm/5bad34/status", 0 /*QoS ของ will*/, true /*retained*/, "offline");
```

- **keep-alive:** บอร์ดส่ง ping ทุก 30 วินาที ถ้า broker ไม่ได้ยินอะไรเกินประมาณ 1.5 เท่า (≈ 45 วินาที) ถือว่าหลุดและประกาศ LWT
- **QoS:** 0 = ส่งครั้งเดียว ไม่รับประกัน (Lab นี้ใช้ เพราะ telemetry เป็นค่าที่มาใหม่เรื่อยๆ) ; 1 = อย่างน้อยหนึ่งครั้ง (อาจซ้ำ) ; 2 = ครั้งเดียวพอดี (หนักสุด)

### 3.4.1 รหัสสถานะของ PubSubClient (`mqtt.state()` / `rc=`)

| rc | ความหมาย |
|---|---|
| 0 | เชื่อมต่อแล้ว |
| −1 | ตัดการเชื่อมต่อ |
| −2 | เชื่อมต่อไม่สำเร็จ (broker ไม่ตอบ / ชื่อ/พอร์ตผิด / เครือข่ายมีปัญหา) |
| −3 | การเชื่อมต่อขาดระหว่างใช้งาน |
| −4 | หมดเวลารอ broker |
| 1–5 | broker ปฏิเสธ (โปรโตคอลผิด, client id ผิด, ไม่พร้อม, ชื่อ/รหัสผ่านผิด, ไม่ได้รับอนุญาต) |

### 3.7 ความปลอดภัยของคำสั่ง

คำสั่งที่มาจากเครือข่ายเป็น "ข้อมูลที่เชื่อไม่ได้" มาตรการใน Lab นี้:

| มาตรการ | อยู่ในโค้ดที่ไหน |
|---|---|
| ปิดรับคำสั่งเป็นค่าเริ่มต้น เปิดได้จากบนจอหรือ Serial เท่านั้น | ตัวแปร `remoteEnabled` = false เมื่อเปิดเครื่อง, ปุ่ม `REMOTE`, คำสั่ง `r` |
| หมดอายุเอง 10 นาที | `REMOTE_ENABLE_MS`, `updateRemoteExpiry()` (เทียบเวลาแบบมีเครื่องหมาย ไม่พังเมื่อ `millis()` ล้น) |
| คำสั่งทุกตัวตอบ `ack` พร้อมเหตุผล | `mqttReply()` |
| กรองข้อมูล: ตัดความยาว, อนุญาตเฉพาะ `A-Z a-z 0-9 _ -`, อักขระอื่นเป็น `?` | `copySafe()` |
| payload ต้องเป็น `ON`/`OFF`/`AUTO` เท่านั้น ชื่อคำสั่งต้องรู้จัก | `mqttCallback()` |
| ปั๊มยังติด watchdog / cooldown | ใช้ตรรกะ MANUAL เดิมของ Lab 10 |
| สำเนา topic/payload ก่อนตอบกลับ | ไลบรารีใช้บัฟเฟอร์เดียวกันกับการส่ง การ publish ตอบกลับจะเขียนทับข้อมูลเดิม |

**ข้อจำกัด:** broker สาธารณะไม่มีรหัสผ่านและไม่เข้ารหัส ใครรู้ชื่อ topic ก็ส่งคำสั่งได้ขณะ REMOTE เปิด และดักอ่านข้อมูลได้ มาตรการข้างบนช่วย "จำกัดความเสียหาย" ไม่ใช่ "ป้องกัน" ของจริงต้องมี user/password + TLS (พอร์ต 8883) และจำกัดสิทธิ์รายอุปกรณ์

### 3.8 เครือข่ายต้องไม่ขัดจังหวะตัวควบคุม

`mqtt.connect()` **หยุดรอ** จนกว่าจะสำเร็จหรือ timeout ถ้า broker ไม่ตอบ จอสัมผัส ตัวควบคุม และ watchdog ของปั๊มจะค้างตลอดช่วงนั้น วัดจากบอร์ดต้นแบบ:

| กรณี | เวลาที่หยุดรอต่อครั้ง |
|---|---|
| broker ปกติ | 542–636 ms |
| IP ที่ไม่ตอบ (ค่าเริ่มต้นของ `WiFiClient`) | 3.0 วินาที |
| ตั้ง `mqttNet.setTimeout(2)` (ค่าในโปรแกรมนี้) | 2.0 วินาที |
| ชื่อ broker ที่ DNS หาไม่เจอ | 15–30 ms |

โปรแกรมลดผลกระทบด้วย **exponential backoff**: ลองใหม่หลัง 5 → 10 → 20 → 40 → 60 → 60 … วินาที (เริ่มนับหลังการลองครั้งก่อนจบ) เมื่อสำเร็จจะรีเซ็ตกลับเป็น 5 วินาที ตัวเลข `BLOCKED last … ms, max … ms` ในหน้า MQTT แสดงเวลาที่หยุดรอ

ทางแก้ที่เหมาะกว่า (ไม่ได้ทำใน Lab นี้) คือแยกงานเครือข่ายไปอยู่ใน task ของ FreeRTOS อีกตัว ซึ่งต้องจัดการข้อมูลที่ใช้ร่วมกันให้ปลอดภัย

## 6. แบบฝึกหัด

ก่อนแก้ทุกข้อให้จดสภาพเดิมไว้เทียบ ทำทีละข้อ (แก้ → build/upload → ดูผลใน MQTT client → ย้อนกลับ)

### ระดับ 1 — พื้นฐาน (ข้อละ 5 คะแนน)

**ข้อ 1 — wildcard:** ให้ topic ได้แก่ (A) `cydfarm/5bad34/telemetry` (B) `cydfarm/5bad34/cmd/pump` (C) `cydfarm/aaaaaa/telemetry` (D) `cydfarm/5bad34/state/pump` ตัวกรองต่อไปนี้ตรงกับ topic ใดบ้าง : (ก) `cydfarm/5bad34/#` (ข) `cydfarm/+/telemetry` (ค) `cydfarm/5bad34/+` (ง) `+/+/cmd/#` (จ) `#` (ฉ) `cydfarm/+/state/+`

**ข้อ 2 — ปริมาณข้อมูล:** ถ้าเปลี่ยน `MQTT_TELEMETRY_MS` เป็น 3000 ปริมาณข้อมูล telemetry ต่อชั่วโมงและต่อวันเป็นเท่าไร (ใช้ขนาดแพ็กเก็ตจริงของคุณ) และ TX บนหน้า MQTT ควรเพิ่มประมาณกี่ข้อความใน 5 นาที (ทำนายก่อน แล้ววัดจริง)

**ข้อ 3 — ทดลอง broker ที่ไม่ตอบ:** เปลี่ยน `MQTT_HOST` เป็น `"10.255.255.1"` (ที่อยู่ที่ไม่มีเครื่องตอบ) อัปโหลด ดู Serial และหน้า MQTT ตอบ: เวลาที่หยุดรอต่อครั้ง, ช่วงห่างของการลองใหม่ และสิ่งที่ผู้ใช้สังเกตได้บนจอ (แล้วย้อนกลับ)

### ระดับ 2 — ทดลองเข้าใจหลักการ (ข้อละ 7 คะแนน)

**ข้อ 4 — เพิ่ม heap ใน telemetry:** เพิ่มฟิลด์ `heap` (หน่วยความจำว่าง `ESP.getFreeHeap()`) ลงใน JSON ตรวจว่า payload ยังไม่เกินบัฟเฟอร์ รายงานค่า heap ที่เห็นและขนาด payload ใหม่

**ข้อ 5 — คำสั่งตัวเลข `backlight`:** เพิ่มคำสั่ง `<root>/cmd/backlight` รับค่า 10–100 ปรับความสว่างจอ ต้อง **ตรวจค่า** (ปฏิเสธค่านอกช่วงและข้อความที่ไม่ใช่ตัวเลข) และตอบ `ack` ทดสอบด้วย `40`, `5`, `ABC`, `100`

**ข้อ 6 — topic สถานะแบบ retained:** เพิ่ม topic `<root>/state/fan`, `<root>/state/light`, `<root>/state/pump` มีค่า `ON`/`OFF` เป็น **retained** ส่งทุกครั้งที่อุปกรณ์เปลี่ยนสถานะ ทดสอบโดยเปิด client ใหม่ทีหลัง ต้องเห็นสถานะปัจจุบันทันที และอธิบายว่าทำไมถึงควรลบข้อความ retained ที่ค้างจากการทดสอบ

### ระดับ 3 — ออกแบบเอง (ข้อละ 10 คะแนน)

**ข้อ 7 — แผนความปลอดภัยสำหรับของจริง:** เขียนรายงานและโค้ด (ส่วนที่แก้) สำหรับยกระดับความปลอดภัย: (ก) ใช้ broker ที่มี user/password (เก็บใน `secrets.h` ไม่ใส่ในโค้ดหลัก) (ข) การเข้ารหัส TLS ที่พอร์ต 8883 (ใช้ `WiFiClientSecure`) และเรื่องใบรับรอง (ค) จำกัดสิทธิ์: อุปกรณ์เขียนได้เฉพาะ topic ของตัวเอง (ง) ตารางภัยคุกคามอย่างน้อย 4 ข้อและวิธีรับมือ (เช่น ใครก็ส่ง `estop` ได้, ดักอ่านค่า, ส่งคำสั่งซ้ำ (replay), ส่งข้อความจำนวนมาก) หมายเหตุ: ต้องมี broker ส่วนตัวถึงจะทดสอบได้ ถ้าไม่มี ให้ส่งเป็นแผนและโค้ดที่ยังไม่ได้ทดสอบ พร้อมระบุตรงๆ

**ข้อ 8 (โบนัส +10) — ท้าทาย:** เขียนโปรแกรมฝั่งคอมพิวเตอร์ (เช่น Python, Node-RED) ที่ subscribe telemetry เก็บลงไฟล์ CSV และส่งคำสั่งกลับอัตโนมัติ เช่น ถ้า `temp` ≥ 32 ติดต่อกัน 3 ค่า ให้ส่ง `cmd/fan = ON` (ต้องเปิด REMOTE ไว้) แสดงผลและอธิบายความเสี่ยงของการให้โปรแกรมภายนอกควบคุมอุปกรณ์

## 7. คำถามทบทวน (ข้อละ 1 คะแนน)

1. publish/subscribe ผ่าน broker ต่างจากเว็บเซิร์ฟเวอร์บนบอร์ดอย่างไร (อย่างน้อย 3 ข้อ)?
2. wildcard `+` และ `#` ต่างกันอย่างไร และใช้ตอน publish ได้หรือไม่?
3. retained message คืออะไร ใช้กับข้อความแบบไหนและไม่ควรใช้กับแบบไหน?
4. Last Will ทำงานอย่างไร และใครเป็นผู้ประกาศ `offline`?
5. ทำไม client id ต้องไม่ซ้ำ และผลเป็นอย่างไรถ้าซ้ำ?
6. QoS 0, 1, 2 ต่างกันอย่างไร ทำไม Lab นี้เลือก 0?
7. ทำไมคำสั่งจากเครือข่ายจึงต้อง "ปิดเป็นค่าเริ่มต้น หมดอายุเอง และกรองข้อมูล"?
8. ทำไมปั๊มต้องติด watchdog และช่วงพัก แม้คำสั่งจะมาจากผู้ใช้ที่ได้รับอนุญาต?
9. exponential backoff คืออะไรและช่วยแก้ปัญหาอะไรในตัวควบคุมนี้?
10. ความเสี่ยงของ broker สาธารณะที่ไม่มีรหัสผ่านมีอะไรบ้าง และของจริงต้องมีอะไรเพิ่ม?

## 9. ปัญหาที่พบบ่อย

| อาการ | สาเหตุ / วิธีแก้ |
|---|---|
| หน้า MQTT ขึ้น `NO WIFI` | ไม่มี `secrets.h` หรือรหัสผิด/ WiFi เป็น 5 GHz ; ดู Serial `[WIFI]` |
| `RETRY … (rc=-2)` ต่อเนื่อง | ติดต่อ broker ไม่ได้: ตรวจอินเทอร์เน็ต, ชื่อ/พอร์ตของ broker, ไฟร์วอลล์ที่บล็อกพอร์ต 1883 (โรงเรียน/องค์กรมักบล็อก) ; จอจะค้างประมาณ 2 วินาทีทุกครั้งที่ลอง |
| เชื่อมต่อแล้วแต่ไม่เห็นข้อมูลใน client | subscribe topic ผิด (ตรวจรหัส 6 หลักและตัวพิมพ์เล็ก-ใหญ่) หรือเชื่อมต่อคนละ broker/พอร์ต |
| ข้อความ telemetry เก่าค้าง | เป็นข้อความ retained จากครั้งก่อน รอข้อความใหม่ใน 10 วินาที |
| ส่งคำสั่งแล้วตอบ `rejected: REMOTE is OFF` | ยังไม่ได้แตะปุ่ม `REMOTE` บนจอ หรือหมดอายุแล้ว (10 นาที) |
| ส่งคำสั่งแล้วตอบ `unknown command` | ชื่อคำสั่งผิด (ต้องเป็นตัวพิมพ์เล็ก `fan` `light` `pump` `estop`) |
| ไม่มี `ack` กลับมา | ไม่ได้ subscribe `<root>/ack` หรือ `<root>/#` |
| `publish to telemetry failed` ใน Serial | ข้อความใหญ่กว่าบัฟเฟอร์ (ลืม `setBufferSize`) หรือการเชื่อมต่อหลุด |
| บอร์ดสองตัวตัดกันเอง | client id ซ้ำ (ใช้รหัสเดียวกัน) |
| ใครก็ไม่รู้ส่งคำสั่งเข้า topic ของเรา | broker สาธารณะ เปิด REMOTE เฉพาะตอนสาธิต ; ดูคำถามทบทวนข้อ 10 |
| upload ไม่ผ่าน | ปิด Serial Monitor / กด BOOT ค้างตอน `Connecting......` / ถอด-เสียบสาย USB |
