## ขั้นตอนปฏิบัติ — คำตอบที่คาดหวัง

| `MQTT_TELEMETRY_MS` | 10000 (10 วินาที) |
| `MQTT_RECONNECT_MIN_MS` / `MAX_MS` | 5000 / 60000 |
| `MQTT_SOCKET_TIMEOUT_S` / `MQTT_KEEPALIVE_S` | 2 / 30 |
| `REMOTE_ENABLE_MS` | 600000 = 10 นาที |
| `lib_deps` ที่เพิ่ม | `knolleary/PubSubClient@^2.8` |

### ขั้นที่ 2 — Build / calibrate

- `[SUCCESS]` ; ครั้งแรกขึ้นหน้า calibrate (`[CAL] no saved calibration`) เพราะ Lab นี้ใช้ namespace `lab11` ; หลังแตะครบ `[CAL] saved to flash` เข้า DASH
- Serial: `[MQTT] root topic: cydfarm/<รหัส 6 หลัก>` (บอร์ดต้นแบบ `5bad34`) และ `[MQTT] connected (took ~540–670 ms)` ภายใน 2–4 วินาทีหลังเปิดเครื่อง (ต้องรอ WiFi ก่อน)

### ขั้นที่ 3 — หน้า MQTT

| รายการ | ค่าที่คาด (ภาพจากบอร์ดต้นแบบ) |
|---|---|
| STATE | `CONNECTED` (สีเขียว) |
| TOPIC | `cydfarm/5bad34` (ของนักเรียนต่างกัน) |
| TRAFFIC | `TX` เพิ่มทุก 10 วินาที, `RX 0`, `drop` 0 หรือ 1 (เหตุการณ์ที่เกิดก่อนเชื่อมต่อครั้งแรก เช่นพัดลมเริ่มทำงานตอนบูต) |
| BLOCKED | `last ≈ 610 ms, max ≈ 610 ms` (เวลาที่การเชื่อมต่อครั้งแรกทำให้หยุดรอ) |
| จุดสถานะ MQTT | สีเขียว (ซ้ายของจุด heartbeat) |
| ปุ่มล่าง | `REMOTE OFF (tap to allow)` |

### ขั้นที่ 4 — subscribe

- ข้อความที่มาทันที (retained): **`status`** (`online`) และ **`telemetry`** (ค่าล่าสุด) ส่วน `event`/`ack` ไม่มา เพราะไม่ใช่ retained
- ค่า `temp`/`hum`/`light`/`soil` ต้องใกล้เคียงหน้า DASH (ต่างกันได้เล็กน้อยตามจังหวะอัปเดต ≤ 10 วินาที)
- `src` : `REAL` ตรงกับป้าย `REAL` บน DASH ; ถ้าแตะ TEMP เป็น SIM จะเป็น `SIM-RANDOM`/`SIM-SWEEP`
- `rssi` = ความแรงสัญญาณ WiFi (dBm) ค่าติดลบ ยิ่งใกล้ 0 ยิ่งแรง (ตัวอย่าง −45 ถึง −56)

### ขั้นที่ 5 — จังหวะและขนาด

- ช่วงห่าง ≈ **10 วินาที** ตรงกับ `MQTT_TELEMETRY_MS` (ตัวอย่างวัด `ts` ห่างกันทีละ 10 วินาทีพอดี)
- ขนาด: topic `cydfarm/5bad34/telemetry` ยาว 24 ตัวอักษร + payload ตัวอย่าง 250 ไบต์ → `1 + 2 + 2 + 24 + 250 = 279` ไบต์ ; ต่อชั่วโมง = 279 × 360 ≈ **100,440 ไบต์ ≈ 98 KB** (นักเรียนใช้ความยาวของตัวเองได้)

### ขั้นที่ 6 — event

- `pump_on` : `{"event":"pump_on","detail":"SOIL DRY","ts":"…","uptime_s":N}`
- `pump_off` : `detail` เช่น `soil wet enough` (หรือ `schedule finished`, `manual OFF`, `MAX RUN watchdog`)
- event ไม่ควร retained : ผู้ที่เพิ่ง subscribe จะเห็นเหตุการณ์เก่าเหมือนเพิ่งเกิด (เช่นเห็น `pump_on` ทั้งที่ปั๊มดับไปนานแล้ว)
- กด BOOT: โค้ดเรียก `emergencyStop()` ตัวเดียวกับคำสั่ง `estop` ทาง MQTT ซึ่งวัดแล้วได้ event `estop` (`all devices MANUAL OFF`) ตามด้วย event ของอุปกรณ์ที่ถูกดับ (เช่น `fan_off`) — ยังไม่ได้ทดสอบกดปุ่ม BOOT จริง

### ขั้นที่ 7 — คำสั่งตอน REMOTE ปิด

- `ack` : `{"cmd":"pump","payload":"ON","result":"rejected: REMOTE is OFF"}` (วัดจริง)
- หน้า MQTT: `RX` เพิ่ม 1 (นับเมื่อได้รับแม้ถูกปฏิเสธ) และ `LAST CMD` แสดง `pump ON: rejected: REMOTE is OFF` (ตัวหลังอ่านจากโค้ด ยังไม่มีภาพ)
- ปั๊ม **ไม่ทำงาน**

### ขั้นที่ 8 — เปิด REMOTE แล้วสั่งงาน

- ปุ่มเปลี่ยนเป็น `REMOTE ON m:ss (tap = OFF)` สีส้มและนับถอยหลังจาก 10:00 ; แถบหัวมีวงแหวนสีส้มรอบจุด MQTT (ส่วนสีส้มยังไม่มีภาพ)
- ผลคำสั่ง (วัดจริง): ทุกคำสั่ง `accepted` ; `fan ON` → พัดลม 100% (LED น้ำเงินสว่างสุด) ; `AUTO` กลับตามอุณหภูมิ ; `light ON` → ไฟเขียวติด ; `pump ON/OFF` → LED แดง
- เวลา publish → ack ≈ **0.4–0.6 วินาที** (รวมทางไป-กลับผ่านอินเทอร์เน็ต)
- event เพิ่ม: `remote` (enabled) ตอนเปิดปุ่ม, `fan_on`/`light_on`/`pump_on` ฯลฯ ตามอุปกรณ์ และ `remote_cmd` (`detail` เช่น `pump ON: accepted`)
- telemetry : `"remote":true`

### ขั้นที่ 9 — ความปลอดภัย

| ทดสอบ | ผลที่วัดจริง |
|---|---|
| pump ON → OFF → ON ทันที | ครั้งที่ 3: `refused: pump resting N s` (N ≈ 16–20) เพราะหลังหยุดต้องพัก 20 วินาที |
| `pump` = `MAYBE` | `rejected: use ON/OFF/AUTO` |
| `door` = `OPEN` | `rejected: unknown command` |
| `fan` = `on` (พิมพ์เล็ก) | **ยอมรับ** เพราะ `copySafe` แปลง payload เป็นตัวพิมพ์ใหญ่ก่อนเทียบ (ส่วนชื่อคำสั่งต้องพิมพ์เล็ก) — ผลนี้อ่านจากโค้ด ยังไม่ได้ส่งกรณีนี้จริง |
| `estop` = `GO` | `accepted: all MANUAL OFF` ทุกอุปกรณ์ MANUAL + OFF (ดู CTRL) |
| `AUTO` ของทั้ง 3 | `accepted` อุปกรณ์กลับทำตามกฎ |
| แตะ REMOTE ปิดแล้วส่งคำสั่ง | `rejected: REMOTE is OFF` |
| (เสริม) `REMOTE_ENABLE_MS = 60000` | ผ่าน 1 นาที REMOTE ปิดเอง ปุ่มกลับเป็น `REMOTE OFF` Serial `remote commands DISABLED` (**ยังไม่ได้ยืนยันบนบอร์ด**) |

### ขั้นที่ 10 — Last Will

- ลำดับ (วัดจริง) : `status: offline` มาก่อน แล้ว `status: online` (ห่างกัน ≈ 0.6 วินาที) หลังรีเซ็ต
- ผู้ประกาศ `offline` คือ **broker** (จากข้อความ Last Will ที่บอร์ดฝากไว้ตอนเชื่อมต่อ) ไม่ใช่บอร์ด (บอร์ดรีเซ็ตแล้วจึงบอกไม่ได้)
- telemetry ข้อความแรกหลังรีเซ็ต : `uptime_s` ≈ 3 และ `temp`/`hum` = `null`, `src` = `"NONE"` เพราะ DHT11 ยังไม่ได้อ่านครั้งแรก (อ่านทุก 2.5 วินาที) ; telemetry นั้นเป็น retained จึงค้างจนข้อความถัดไปใน 10 วินาที
- REMOTE หลังรีเซ็ต = **OFF** (`"remote":false`) เพราะไม่ได้เก็บสถานะนี้ (ตั้งใจ)

## เฉลยคำถามอ่านโค้ด (หัวข้อ 5)

**5.1** (ก) root = `cydfarm/a1b2c3`, client id = `cydfarm-a1b2c3` (ข) client id ซ้ำ : broker ตัดการเชื่อมต่อของอีกฝั่งทุกครั้งที่อีกตัวเชื่อมต่อ ทั้งสองตัวพยายามต่อใหม่ จึงตัดกันไปมา ; topic เดียวกันทำให้ข้อมูลสองบอร์ดปนกัน และคำสั่งไปถึงทั้งสองตัว (ค) ชื่อตายตัวชนกับคนอื่นบน broker สาธารณะที่ผู้เรียนจำนวนมากใช้พร้อมกัน

**5.2** (ก) ตัวควบคุมทำงานต่อได้ตามปกติ (การ publish ไม่ใช่เงื่อนไขของการควบคุม) เหตุการณ์ถูกทิ้งและนับใน `mqttDropped` (แสดง `drop` ในหน้า MQTT) (ข) เก็บคิวต้องใช้หน่วยความจำและเมื่อเชื่อมต่อใหม่จะส่งข้อความเก่าถล่มทีเดียว ผู้รับอาจเข้าใจว่าเป็นเหตุการณ์ปัจจุบัน ; บอร์ดเล็กไม่ควรสะสมข้อมูลไม่จำกัด (ค) ค่าที่ใส่ใน `detail` ต้องไม่มีอักขระที่ทำให้ JSON เสีย เช่น `"` หรือ `\` และต้องไม่ยาวเกินบัฟเฟอร์ (ที่ Lab นี้ใช้ข้อความคงที่จากโค้ดของเราเองทั้งหมด)

**5.3** (ก) เวลาเริ่มของการลองครั้งที่ 1–8 : 0, 7, 19, 41, 83, 145, 207, 269 วินาที (หลังแต่ละครั้งที่จบ รอ 5, 10, 20, 40, 60, 60, 60 วินาที ตามลำดับ) (ข) 8 ครั้ง × 2 วินาที = **16 วินาที** ใน 300 วินาที ≈ **5.3%** (ถ้าไม่มี backoff ลองทุก 5 วินาที จะหยุดรอ 2 วินาทีในทุกๆ 7 วินาที ≈ 29%)

**5.4** (ก) `snprintf` คืนความยาวที่ "ควรจะเขียน" ถ้าเกินบัฟเฟอร์ ข้อความจะถูกตัดและ JSON ไม่สมบูรณ์ จึงต้องตรวจและไม่ส่ง (ข) `publish` คืนค่าเท็จ ข้อความไม่ถูกส่ง (Serial `publish to telemetry failed`) (ค) ต้องเพิ่มขนาด `char json[420]` และเรียก `mqtt.setBufferSize(...)` ให้ใหญ่ขึ้น (เช่น 640) ; แพ็กเก็ต = 1 + 2 + 2 + 24 + 480 = 509 ไบต์ ซึ่งใกล้เต็มบัฟเฟอร์ 512 ควรเพิ่มอีก

**5.5** (ก) `ON??` (ตัวอักษรถูกแปลงเป็นตัวพิมพ์ใหญ่ `ON"}` แล้ว `"` และ `}` เป็นอักขระที่ไม่อนุญาตจึงกลายเป็น `?`) ผลคือไม่ตรงกับ `ON`/`OFF`/`AUTO` → ถูกปฏิเสธ (ข) ขนาดของ `data` คือ 16 ไบต์ จึงเก็บได้สูงสุด **15 ตัวอักษร** (เหลือ 1 ไบต์สำหรับ `\0`) (ค) ชื่อคำสั่งไม่ถูกแปลงเป็นตัวพิมพ์ใหญ่ `Pump` ≠ `pump` → `rejected: unknown command` (ง) ไลบรารีใช้บัฟเฟอร์เดียวกันรับและส่ง การ publish ตอบกลับจะเขียนทับ topic/payload เดิมที่ตัวแปร `topic`/`payload` ชี้อยู่

**5.6** (ก) 100,000 + 600,000 = **700,000 ms** (ข) `millis()` ล้นกลับเป็น 0 ทุก 2³² ms ≈ **49.7 วัน** การเทียบด้วยผลต่างแบบมีเครื่องหมายยังถูกต้องแม้ล้น ส่วน `now >= remoteUntil` จะผิดเมื่อ `remoteUntil` ล้นไปแล้วแต่ `now` ยังไม่ล้น

**5.7** (ก) ยอมรับ → พัดลม MANUAL ON 100% (ข) ยอมรับ → ไฟกลับ AUTO (ค) `refused: pump resting N s` (ง) `accepted: all MANUAL OFF` (จ) `rejected: unknown command` (ฉ) `rejected: use ON/OFF/AUTO`

**5.8** (ก) retained: `status` และ `telemetry` (สถานะล่าสุด) ; `event`/`ack` ไม่ retained เพราะเป็นเหตุการณ์ครั้งเดียว ผู้ที่มาทีหลังจะเห็นของเก่าเหมือนเพิ่งเกิด (ข) `id` = client id ; `user` = `nullptr` (ไม่มี) ; `pass` = `nullptr` ; `willTopic` = topic `status` ; `0` = QoS ของข้อความ will ; `true` = retained ; `"offline"` = ข้อความ will (ค) subscribe `<root>/cmd/#` → publish `status = online` (retained) → ตั้ง `lastTelemetryAt` ให้ส่ง telemetry ข้อความแรกทันที

**5.9** (ก) `mqtt.disconnect()` แล้วตั้งสถานะ `NoWifi` (Serial `WiFi lost: MQTT stopped`) เมื่อ WiFi กลับมาจะเข้าสถานะรอแล้วลองเชื่อมต่อใหม่ (ข) แสดง `connection lost (rc=…)` เปลี่ยนเป็นสถานะรอ และตั้งเวลาลองใหม่หลัง 5 วินาที (ค) `mqtt.loop()` รับแพ็กเก็ตที่เข้ามา (เรียก `mqttCallback`) และส่ง ping ตาม keep-alive ต้องเรียกถี่กว่ารอบ keep-alive มาก (ที่นี่เรียกทุกรอบของ `loop()`)

**5.10** (ก) การตรวจ watchdog ถูกเลื่อนได้สูงสุดประมาณ 2 วินาที ปั๊มอาจเดินถึง ≈ 32 วินาทีในกรณีเลวร้ายสุด ซึ่งยังน้อยกว่าความเสียหายที่ watchdog ป้องกัน แต่ต้องรู้ว่าไม่ใช่ 30 วินาทีเป๊ะ (ข) จอสัมผัสไม่ตอบสนอง การแตะที่เกิดในช่วงนั้นพลาด/ล่าช้า (ค) แยกงานเครือข่ายไปอยู่ใน task FreeRTOS อีกตัว (อีกคอร์ส) หรือใช้ไลบรารีเชื่อมต่อแบบ asynchronous (non-blocking) หรือเชื่อมต่อเฉพาะตอนผู้ใช้ไม่ได้แตะจอ

### ข้อ 2 — ปริมาณข้อมูล (5 คะแนน)

ทุก 3 วินาที = 20 ข้อความต่อนาที × 279 ไบต์ = 5,580 ไบต์ต่อนาที = **334,800 ไบต์ต่อชั่วโมง ≈ 327 KB** ; ต่อวัน ≈ 8,035,200 ไบต์ ≈ **7.7 MB** (เทียบกับ 98 KB ต่อชั่วโมง ที่ 10 วินาที) TX เพิ่มใน 5 นาที ≈ 100 ข้อความ (+ event) เทียบกับ ≈ 30 ที่ 10 วินาที ให้ค่า 5% คลาดเคลื่อนได้ (นับ event และข้อความ `status` ด้วย)

### ข้อ 3 — broker ที่ไม่ตอบ (5 คะแนน)

ตั้ง `MQTT_HOST = "10.255.255.1"` ผลวัดจริง: `connect failed rc=-2 (took 2007 ms), retry in 5 s` แล้ว 10 s, 20 s (และ 40 s) ; ผู้ใช้เห็นหน้า MQTT เป็น `RETRY Ns (rc=-2)` และจอสัมผัสไม่ตอบ ≈ 2 วินาทีทุกครั้งที่ลอง ; ตัวควบคุมยังทำงานต่อเนื่อง (พัดลมยังตามอุณหภูมิ) ยกเว้นช่วงหยุดรอ

### ข้อ 4 — heap ใน telemetry (7 คะแนน) — ทดสอบบนบอร์ดแล้ว

```cpp
// ใน publishTelemetry(): เพิ่มท้ายรูปแบบ JSON
"\"remote\":%s,\"rssi\":%d,\"heap\":%lu}"
// และท้ายรายการอาร์กิวเมนต์
..., WiFi.RSSI(), static_cast<unsigned long>(ESP.getFreeHeap()));
```

ผลวัดจริง: `"heap":239660` (ที่ uptime 3 วินาที) และ `242780` (ภายหลัง) ≈ 234–237 KB payload เพิ่มอีก 14 ไบต์ (250 → 264 ไบต์) ยังไม่เกิน `char json[420]` และบัฟเฟอร์ 512
สิ่งที่ต้องตรวจ: ขนาด payload เทียบบัฟเฟอร์ทั้งสองจุด (ตัวแปร `json` และ `setBufferSize`) และชนิดของ `%lu` ให้ตรงกับ `unsigned long`

### ข้อ 5 — คำสั่ง `backlight` (7 คะแนน) — ทดสอบบนบอร์ดแล้ว

```cpp
// ใน mqttCallback() ก่อนสาขา estop
} else if (strcmp(cmd, "backlight") == 0) {
    const int percent = atoi(data);
    if (percent < app::BACKLIGHT_MIN_PERCENT || percent > 100) {
        mqttReply(cmd, data, "rejected: use 10..100");
        return;
    }
    applyBacklight(percent);
    mqttReply(cmd, data, "accepted");
}
```

ผลวัดจริง (REMOTE เปิด): `40` → `accepted` ; `5` → `rejected: use 10..100` ; `ABC` → `rejected: use 10..100` (`atoi("ABC")` = 0 ต่ำกว่า 10) ; `100` → `accepted`
ประเด็น: ตรวจค่านอกช่วง (ปฏิเสธ ไม่ใช่บีบค่าเงียบๆ) ; `copySafe` ทำให้ payload เป็นตัวพิมพ์ใหญ่/ตัวเลขเท่านั้นก่อนแปลง ; ตอบ `ack` ทุกกรณี ; คำสั่งตัวเลขนี้ไม่ได้บันทึกลง flash (ต่างจากการปรับด้วยแถบเลื่อน)

### ข้อ 6 — topic สถานะแบบ retained (7 คะแนน) — ทดสอบบนบอร์ดแล้ว

```cpp
// ใน publishEvent() ต่อจาก mqttSend("event", json, false);
const char *stateTopic = nullptr;
if (strncmp(name, "fan_", 4) == 0) stateTopic = "state/fan";
else if (strncmp(name, "light_", 6) == 0) stateTopic = "state/light";
else if (strncmp(name, "pump_", 5) == 0) stateTopic = "state/pump";
if (stateTopic != nullptr) mqttSend(stateTopic, strstr(name, "_on") != nullptr ? "ON" : "OFF", true);
```

ผลวัดจริง: เมื่อ subscribe ใหม่ ได้ `state/fan = ON` ทันที (retained) ; สั่ง `pump ON` → `state/pump = ON` และ `OFF` → `state/pump = OFF`
ข้อสังเกต: ต้องลบข้อความ retained ที่ค้างหลังทดสอบ โดย publish payload **ว่าง** แบบ retained ไปที่ topic นั้น (ผมทำแล้วหลังทดสอบ) ไม่งั้นค่าเก่าค้างบน broker สาธารณะ ; สถานะที่ส่งมีเฉพาะตอนมีการเปลี่ยน ดังนั้นหลังเปิดเครื่อง อุปกรณ์ที่ไม่เคยเปลี่ยนจะไม่มี topic สถานะ (ข้อจำกัดที่นักเรียนควรสังเกต)

### ข้อ 7 — แผนความปลอดภัยสำหรับของจริง (10 คะแนน) — ไม่มีเฉลยที่ทดสอบ

แนวคิดที่ยอมรับได้ (ตรวจความถูกต้องของเหตุผล ไม่ใช่รูปแบบ):

- **user/password:** เก็บใน `secrets.h` (เช่น `MQTT_USER`, `MQTT_PASSWORD`) ส่งเป็นอาร์กิวเมนต์ที่สองและสามของ `mqtt.connect()` ; ไม่ใส่ในโค้ดหลักหรือ commit ; ใช้รหัสเฉพาะอุปกรณ์
- **TLS:** ใช้ `WiFiClientSecure` กับพอร์ต 8883 และตรวจใบรับรอง (CA) ; ระวังไม่ใช้ `setInsecure()` ในของจริง ; TLS ใช้หน่วยความจำและเวลาเชื่อมต่อมากขึ้น
- **จำกัดสิทธิ์ (ACL):** อุปกรณ์เขียนได้เฉพาะ `<root>/telemetry|status|event|ack` อ่านได้เฉพาะ `<root>/cmd/#` ; ผู้ควบคุมเขียนได้เฉพาะ `cmd/#` — ตั้งที่ broker
- **ตารางภัยคุกคาม (ตัวอย่าง):** ใครก็ส่ง `estop` ได้ → ต้องมี auth/ACL ; ดักอ่านข้อมูล → TLS ; replay (ส่งคำสั่งเก่าซ้ำ) → เพิ่ม timestamp/nonce และปฏิเสธคำสั่งที่เก่า ; ส่งคำสั่งถี่ๆ (flood) → จำกัดอัตรา ; broker ล่ม → ตัวควบคุมต้องทำงานเองได้ (Lab นี้ทำได้) ; สวมรอย client id → auth
- ต้องระบุตรงๆ ว่าไม่ได้ทดสอบกับ broker ส่วนตัว ถ้าไม่มี (เคลมว่าทดสอบแล้วโดยไม่มีหลักฐาน ให้หักคะแนน)

### ข้อ 8 (โบนัส) — โปรแกรมควบคุมจากภายนอก (+10) — ไม่มีเฉลยที่ทดสอบ

แนวทางที่ถูกต้อง: ใช้ไลบรารี MQTT ของภาษาที่เลือก (เช่น paho-mqtt ใน Python) subscribe `<root>/telemetry` แปลง JSON เก็บ CSV มีตัวนับค่าที่ติดต่อกัน (≥ 32 °C 3 ค่า) แล้ว publish `cmd/fan = ON` ครั้งเดียว ไม่ส่งซ้ำทุกข้อความ และมีเงื่อนไขกลับ (เช่น ต่ำกว่า 30 ส่ง `AUTO`)
ความเสี่ยงที่ควรระบุ: โปรแกรมภายนอกล่ม/ค้าง ทิ้งอุปกรณ์ในสถานะ MANUAL ; ลูปควบคุมผ่านอินเทอร์เน็ตมีความหน่วงและอาจขาดหาย ; REMOTE หมดอายุใน 10 นาที (ต้องให้ผู้ใช้เปิดซ้ำ) ; ความเสี่ยงด้านความปลอดภัยของ broker สาธารณะ

## เฉลยคำถามทบทวน

1. ไม่ต้องรู้ IP/เปิดพอร์ตของบอร์ด (บอร์ดต่อออกไปหา broker ผ่าน NAT ได้) ; ผู้ดูหลายคนพร้อมกันโดยบอร์ดส่งครั้งเดียว ; มี Last Will/retained สำหรับสถานะ ; ผู้ส่งและผู้รับไม่ต้องออนไลน์พร้อมกัน (ผ่าน retained) ; ข้อเสีย: พึ่ง broker, หน่วงกว่า, ต้องดูแลความปลอดภัยของ broker
2. `+` แทนหนึ่งระดับ ; `#` แทนทุกระดับที่เหลือ (ต้องอยู่ท้ายสุด) ; ใช้ได้เฉพาะตอน **subscribe** ตอน publish ต้องระบุ topic เต็ม
3. broker เก็บข้อความล่าสุดไว้ส่งให้ผู้ที่ subscribe ทีหลัง ; ใช้กับ "สถานะปัจจุบัน" (status, telemetry) ; ไม่ใช้กับเหตุการณ์/คำสั่งครั้งเดียว (event, ack, cmd)
4. บอร์ดฝากข้อความ `offline` (retained) ไว้กับ broker ตอนเชื่อมต่อ ; ถ้าบอร์ดหลุดโดยไม่ปิดการเชื่อมต่ออย่างเรียบร้อย (ไฟดับ/WiFi ขาด/รีเซ็ต) **broker** เป็นผู้ประกาศ
5. broker ใช้ client id แยกการเชื่อมต่อ ; ถ้าซ้ำ broker ตัดการเชื่อมต่อเดิมเมื่อมีตัวใหม่เข้ามา ทั้งสองจะตัดกันไปมาเมื่อต่อใหม่
6. 0 = ส่งครั้งเดียวไม่รับประกัน ; 1 = อย่างน้อยหนึ่งครั้ง (อาจซ้ำ) ; 2 = ครั้งเดียวพอดี ; Lab นี้เลือก 0 เพราะ telemetry มาใหม่ทุก 10 วินาที ถ้าหายหนึ่งข้อความก็ไม่เสียหาย และไม่ต้องจัดการข้อความซ้ำ
7. คำสั่งจากเครือข่ายเป็นข้อมูลที่เชื่อไม่ได้และผู้ส่งอาจไม่ใช่เจ้าของ ; ปิดเป็นค่าเริ่มต้นและหมดอายุเองลดช่วงเวลาที่เสี่ยง ; กรองข้อมูลกันข้อความผิดรูป/ประสงค์ร้ายทำให้ระบบเพี้ยน
8. ผู้ใช้ที่ได้รับอนุญาตอาจพลาด (ลืมปิด ส่งซ้ำ) หรือบัญชี/ช่องทางถูกบุกรุก ; ข้อจำกัดของฮาร์ดแวร์ (ป้องกันปั๊มเดินเกิน/เปิดปิดถี่) ต้องอยู่ที่ตัวอุปกรณ์ ไม่ขึ้นกับผู้สั่ง
9. หลังเชื่อมต่อไม่สำเร็จ รอนานขึ้นเป็นสองเท่าทุกครั้งจนถึงเพดาน ; ลดจำนวนครั้งที่โปรแกรมต้องหยุดรอเมื่อเครือข่ายหรือ broker ใช้ไม่ได้ (5.3% แทน ≈ 29% ในสถานการณ์ตัวอย่าง) และไม่ถล่ม broker
10. ใครก็อ่านข้อมูลและส่งคำสั่งได้ ; ปลอมตัวเป็นอุปกรณ์/ส่งข้อมูลเท็จ ; ดักอ่านเพราะไม่เข้ารหัส ; ข้อความ retained ค้างและถูกเขียนทับโดยคนอื่นได้ ; ของจริงต้องมี user/password รายอุปกรณ์ + TLS (8883) + ACL
