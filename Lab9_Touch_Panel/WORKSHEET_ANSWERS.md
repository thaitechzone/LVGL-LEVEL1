## ขั้นตอนปฏิบัติ — คำตอบที่คาดหวัง

### ขั้นที่ 1 — ค่าตั้งค่า

| ค่า | ที่มา |
|---|---|
| `TOUCH_PIN_CLK` / `MISO` / `MOSI` / `CS` / `IRQ` | 25 / 39 / 32 / 33 / 36 |
| `TOUCH_SPI_FREQUENCY` | 2,500,000 Hz = 2.5 MHz |
| `TOUCH_Z_MIN` / `TOUCH_POLL_MS` | 400 / 10 ms |
| `TOUCH_PRESS_SAMPLES` / `TOUCH_RELEASE_SAMPLES` | 2 / 3 |
| `CAL_MARGIN` / `CAL_SAMPLES` / `CAL_MIN_SPAN` / `CAL_MAX_ERROR_PX` | 20 / 10 / 300 / 25 |
| `LONG_PRESS_MS` / `REPEAT_DELAY_MS` / `REPEAT_INTERVAL_MS` | 1000 / 500 / 150 ms |
| `BACKLIGHT_MIN_PERCENT` / `BACKLIGHT_CHANNEL` | 10 / 2 |

(ถ้านักเรียนเปิดไฟล์แล้วตัวเลขต่างจากนี้ ให้ดูว่าไฟล์ถูกแก้จากแบบฝึกหัดก่อนหน้าหรือไม่)

### ขั้นที่ 2 — Build / Upload

- ต้องขึ้น `[SUCCESS]` ; คำเตือน `TOUCH_CS pin not defined` ปกติ (ไดรเวอร์จอสัมผัสเขียนเองในโปรแกรม ไม่ได้ใช้ของ TFT_eSPI)
- บอร์ดใหม่ (ยังไม่เคยบันทึก) เริ่มที่ **หน้า calibrate** เพราะ Serial พิมพ์ `[CAL] no saved calibration: the calibration screen will start` ถ้าเคยรัน Lab 9 มาแล้วจะข้ามไปหน้า DASH ทันที (`[CAL] loaded from flash: ...`) ซึ่งยอมรับได้ ให้นักเรียนสั่ง `c` เพื่อ calibrate ใหม่ในขั้นที่ 4

### ขั้นที่ 3 — `z` ขณะไม่แตะ

- คาดหวังต่ำกว่า 400 ทุกครั้ง บอร์ดต้นแบบได้ราว 7–13 (`touching=no`)
- ถ้าเกิน 400 ขณะไม่แตะ แปลว่า: มีการแตะค้างอยู่ (ฟิล์มจอกดทับ/กรอบเคสกดจอ), สายหรือขา SPI ผิด/หลวม หรือชิปไม่ตอบ (MISO ลอย) ให้ตรวจก่อนทำขั้นต่อไป

### ขั้นที่ 4 — calibrate

- ค่าดิบแต่ละจุดควรอยู่ในช่วงราว 400–3700 (ของบอร์ดต้นแบบ: ซ้าย/ขวาคือ ≈ 424–3,664 และ ≈ 497–3,567 ในสองครั้ง, บน/ล่าง ≈ 563–3,520 และ ≈ 703–3,486 ที่ย้อนกลับจากสมการ) และ **ควรได้ `swapXY=no`** ตามบอร์ดต้นแบบ
- `worst target error` ที่โปรแกรมพิมพ์ปกติต่ำ เพราะสมการคำนวณจากจุดเดียวกัน (เป็นการตรวจความเป็นสี่เหลี่ยม ไม่ใช่ความแม่นยำของจอ)
- ต้องเห็น `[CAL] saved to flash (Preferences)` แล้วเข้าหน้า DASH หลังแสดง "Calibration saved" 1.5 วินาที
- การคำนวณด้วยมือ (วิธีเฉลย 5.4) ควรตรงกับที่โปรแกรมพิมพ์ในทศนิยม 4 ตำแหน่ง (`xb`, `yb`) และ 1 ตำแหน่ง (`xa`, `ya`) เพราะโปรแกรมใช้เฉลี่ยของ 2 จุดต่อขอบ (ซ้าย = จุด 1 และ 4, ขวา = จุด 2 และ 3, บน = จุด 1 และ 2, ล่าง = จุด 3 และ 4)
- คำตอบ "แกนสลับหรือไม่": เทียบ `|raw2.x − raw1.x|` กับ `|raw2.y − raw1.y|` ถ้าแกน y เปลี่ยนมากกว่า = สลับ (บอร์ดนี้ในทดสอบคือไม่สลับ)

### ขั้นที่ 5 — ความแม่นยำ

| ตำแหน่ง | คาด |
|---|---|
| กลางกล่องวาด | ≈ (160, 145) |
| มุมบนซ้าย / บนขวาของกล่อง | ≈ (8, 92) / (311, 92) |
| ปุ่ม BACK / CLEAR ตรงกลาง | ≈ (82, 220) / (238, 220) |

- เกณฑ์ตรวจ: **คลาดเคลื่อนไม่เกิน ~10–15 พิกเซลถือว่าสมเหตุสมผล** (เป็นแนวทาง ไม่ใช่ค่าที่วัด; ค่า calibrate บอร์ดต้นแบบสองครั้งต่างกันราว 6–10 พิกเซล) ถ้าคลาดเกิน 25 ควรให้ calibrate ใหม่
- เส้นที่ลากเป็นจุดห่าง/ต่อเนื่อง: วาดวงกลมรัศมี 2 ที่พิกัดใหม่ทุกครั้งที่พิกัดเปลี่ยน อ่านทุก 10 ms ดังนั้น ลากช้าจะติดกัน ลากเร็วจะเห็นจุดห่างเป็นช่วงๆ (ไม่มีการลากเส้นเชื่อมจุด) และผ่านตัวกรอง EMA ทำให้เส้นนุ่มขึ้นแต่ตามนิ้วช้าลงเล็กน้อย

### ขั้นที่ 6 — หน้า DASH

| แตะ | ผล |
|---|---|
| การ์ดเวลา | `requestNtpNow` ถ้ามี WiFi จะขึ้น `[NTP]...` ถ้าไม่มี WiFi จะไม่ได้เวลา |
| การ์ด TEMP หรือ HUMIDITY | `cycleSimChoice()` วนสามสถานะ: ใช้ DHT11 จริง → random → sweep → (กลับ) จริง (การ์ดทั้งสองสลับ**ตัวเดียวกัน**) Serial `[SIM] random: ...` / `[SIM] sweep: ...` / `[SIM] off: ...` |
| การ์ด FAN | `toggleMode()` AUTO ↔ MANUAL |
| ช่องว่างระหว่างการ์ด (x ≈ 160) | ไม่มี widget Serial `target=-` |

(ถ้าไม่มี DHT11 จริง ป้ายอาจเป็น `SIM`/`NONE` อยู่แล้ว ให้ตรวจจากป้ายและ Serial แทน)

### ขั้นที่ 7 — หน้า FAN

| ทดสอบ | เฉลย |
|---|---|
| ลากแถบไปกลางราง | duty ≈ 50% และโหมดสลับเป็น MANUAL เอง (`manualDuty()` เรียก `setMode(Manual)`) |
| ลากสุดซ้าย/ขวา | 0% / 100% (บีบด้วย `constrain`) |
| แตะ `+` ของ ON | เพิ่ม 1 °C ทันที (`onPress`) |
| กด `+` ของ ON ค้าง 1 วินาที เริ่มจาก 30 | ครั้งที่ 1 ทันที (0 ms) + ครั้งที่ 2–5 ที่ ≈ 500, 650, 800, 950 ms = **5 ครั้ง → 35 °C** ซึ่งเป็นเพดานเพราะ `FAN_FULL_TEMP_C − 1 = 35` (กดค้างต่อก็ไม่เพิ่ม) นักเรียนจับเวลาด้วยมืออาจได้ 4–5 ครั้ง ยอมรับ ±1 |
| กด `-` ของ OFF ค้างจนหยุด | หยุดที่ **15 °C** (`THRESHOLD_MIN_C`) ถ้าเริ่มที่ 28 ใช้ 13 ครั้ง ≈ 0.5 + 12 × 0.15 ≈ 2.3 วินาที ส่วน `-` ของ ON หยุดที่ OFF + 1 และ `+` ของ OFF หยุดที่ ON − 1 |
| แตะ `AUTO` | โหมดกลับ AUTO พัดลมตามอุณหภูมิ |

### ขั้นที่ 8 — หน้า SYSTEM

| ทดสอบ | เฉลย |
|---|---|
| ซ้ายสุด | 10% (`BACKLIGHT_MIN_PERCENT`) จอหรี่แต่ยังเห็น |
| กลางราง | x = 160 → fraction = (160 − 24) × 100 ÷ 272 = 50 → 10 + 50 × 90 ÷ 100 = **55%** |
| ปล่อยนิ้ว | `[UI] backlight 55% saved` (ค่าจริงขึ้นกับตำแหน่งที่ปล่อย) |
| แตะ RECALIBRATE สั้นๆ | ไม่เกิดอะไร (ปุ่มถูกกด แต่ไม่ครบ 1000 ms ; การปล่อยไม่เรียก `beginCalibration`) |
| กดค้าง 1 วินาที | แถบเขียวเต็ม Serial `[UI] long press: starting touch calibration` เข้าหน้า calibrate (ต้องใช้ ≈ 1 วินาที ± เวลาตอบสนองของคน) |

ค่า calibrate ครั้งใหม่ต่างจากครั้งแรกได้หลายสิบหน่วยดิบ (บอร์ดต้นแบบ: `x: 0.0861*u−16.5` → `x: 0.0909*u−25.2`) สาเหตุ: ตำแหน่งแตะ/แรงกด/ปลายนิ้วไม่เท่ากัน

### ขั้นที่ 9 — ปล่อยนอกปุ่ม (ผลคาดจากโค้ด ยังไม่ได้ลองบนบอร์ด)

- เลื่อนนิ้วออกนอกปุ่ม: `pressedWidget` เป็น None → ปุ่มกลับสีปกติ ; ปล่อยแล้ว `releasedOn != pressTarget` → Serial `(not a click)` และไม่เรียก `onActivate`
- แท็บ: เหมือนกัน ไม่เปลี่ยนหน้า
- แถบเลื่อน: `onHold(FanSlider)` ถูกเรียกตราบที่ `touch.down` และ `pressTarget` ยังเป็นแถบ **ไม่เช็คว่านิ้วอยู่ในกรอบ** ดังนั้นลากออกนอกแถบแนวตั้งก็ยังตามนิ้วตามแกน x (พฤติกรรมอ่านจากโค้ด; ผู้เขียนยังไม่ได้ลองยืนยัน)
- หมายเหตุ: ถ้านักเรียนสังเกตต่างจากนี้ ให้ขอให้แนบ Serial `[TOUCH] up ...`

### ขั้นที่ 10 — การจำค่า

- หลังรีเซ็ต: `[CAL] loaded from flash: ...` และเข้าหน้า DASH เอง ; `bl=` ตรงกับที่ตั้ง (ตรวจแล้วจากบอร์ดต้นแบบ)
- เกณฑ์ ON กลับเป็นค่าเริ่มต้น (30) และโหมดกลับ AUTO เพราะไม่ได้บันทึก — เป็นการออกแบบ: เกณฑ์เป็นค่าที่ปรับชั่วคราว ถ้าบันทึกทุกครั้งที่กดปุ่ม (อาจกดรัว 5+ ครั้ง/วินาทีด้วย auto-repeat) จะเขียน flash ถี่เกินไป

## เฉลยคำถามอ่านโค้ด (หัวข้อ 5)

**5.1** (ก) `rawX/rawY` = ค่าดิบจาก ADC 12 บิต (0–4095); `x, y` = พิกัดพิกเซลบนจอ (0–319, 0–239) หลังแปลงด้วย calibration และกรอง EMA (ข) `pressEdge`/`releaseEdge` เป็นจริง **รอบเดียว** ในการเรียก `pollTouch()` ที่ตรวจเจอการเปลี่ยนสถานะ (ฟังก์ชันตั้งเป็น false ตอนเริ่มทุกครั้ง) เรียก "edge" เพราะบอก "ขณะที่เปลี่ยน" ไม่ใช่ "สถานะที่เป็นอยู่" (ใช้ `down` แทนสถานะ) (ค) `lastX/lastY` = พิกัดล่าสุดตอนยังแตะอยู่ ใช้ตอนปล่อยเพื่อหาว่าปล่อยบน widget ไหน (หลังปล่อย `touch.x/y` ไม่อัปเดตแล้ว) และแสดง `PIXEL last` ในหน้า TOUCH TEST

**5.2** (ก) z = 500 + 4,095 − 3,800 = **795** ≥ 400 → แตะ (ข) z = 8 + 4,095 − 4,090 = **13** < 400 → ไม่แตะ (ค) ชิปส่งผล 12 บิตชิดซ้ายในคำ 16 บิต (มีบิตศูนย์นำหน้า 1 บิต และ 3 บิตท้ายไม่ใช้) การเลื่อนขวา 3 บิตจึงได้ค่า 0–4095

**5.3** (ก) ระยะห่าง: |2000−2400| = 400, |2000−2010| = 10, |2400−2010| = 390 → คู่ที่ใกล้สุดคือ 2000 กับ 2010 → (2000 + 2010) ÷ 2 = **2005** (ข) 1000 กับ 1010 → **1005** เหตุผล: เฉลี่ยทั้งสามจะถูกค่าที่เพี้ยนดึงไป เช่น ข้อ (ข) ได้ (1000 + 1010 + 1500) ÷ 3 ≈ 1,170 ห่างจากค่าจริงราว 165 หน่วย การเลือกสองค่าที่ใกล้กันเป็นตัวกรองค่าที่โดดแบบง่าย (ชนิด median-ish)

**5.4** จุดดิบ: P1 (480,600), P2 (3600,610), P3 (3590,3530), P4 (470,3520)
(ก) dxTop = |3600 − 480| = 3,120, dyTop = |610 − 600| = 10 → dyTop ไม่มากกว่า dxTop → `swapXY = false`
(ข) `leftU` = (480 + 470) ÷ 2 = **475**, `rightU` = (3600 + 3590) ÷ 2 = **3,595**, `topV` = (600 + 610) ÷ 2 = **605**, `bottomV` = (3530 + 3520) ÷ 2 = **3,525** (spanU = 3,120, spanV = 2,920 ผ่านเกณฑ์ ≥ 300)
(ค) `xb` = 279 ÷ 3,120 = **0.0894**, `xa` = 20 − 0.089423 × 475 = **−22.5**, `yb` = 199 ÷ 2,920 = **0.0682**, `ya` = 20 − 0.068151 × 605 = **−21.2**
(ง) P2 = (620, 3600): dxTop = |620 − 480| = 140, dyTop = |3600 − 600| = 3,000 → `swapXY = true` แล้วคำนวณต่อด้วยแกนสลับ (u = rawY, v = rawX) ผลคือ P1 จะอยู่ห่างเป้าอย่างน้อย ≈ 270 พิกเซล (u = 600 → x ≈ −251 เทียบเป้า 20) เกินเกณฑ์ 25 → `Calibration FAILED`/"points are not consistent with a rectangle" ให้ทำใหม่ (ข้อนี้สอนว่าแตะผิดลำดับ/ผิดมุมจะถูกจับได้)

**5.5** ลำดับตัวอย่าง (ตัวอย่างที่ 1 ที่เวลา 0 ms): `T T T N T T N N N`
(ก) กดลงที่ **ตัวอย่างที่ 2** (T ติดกัน 2 ตัว) เวลา ≈ 10 ms นับจากตัวอย่างแรก (ใช้หลักฐานการแตะ 2 ตัวอย่าง ≈ 20 ms ซึ่งเป็นค่าหน่วงของ debounce) (ข) ปล่อยที่ **ตัวอย่างที่ 9** (N ติดกัน 3 ตัว คือตัวที่ 7, 8, 9) (ค) **ไม่** เพราะ N ตัวที่ 4 ตัวเดียว ตัวนับ `releaseCount` = 1 แล้วถูกตั้งเป็น 0 ทันทีที่ตัวอย่างที่ 5 เป็น T (ต้อง N ติดกัน 3 ตัวถึงปล่อย) จึงไม่เกิดการปล่อยหลอกจากสัญญาณสะดุดครั้งเดียว

### ข้อ 1 — สี (5 คะแนน)

- RGB565 ของ `rgb565(34, 48, 68)`: r = 34 → `34 & 0xF8` = 32 → `<< 8` = 0x2000 ; g = 48 → `48 & 0xFC` = 48 → `<< 3` = 0x0180 ; b = 68 → `68 >> 3` = 8 = 0x0008 → รวม **0x2188**
- ตัวอย่างสีใหม่ `rgb565(60, 40, 80)`: r → `60 & 0xF8` = 56 → 0x3800 ; g → 40 → `<< 3` = 0x0140 ; b → `80 >> 3` = 10 = 0x000A → **0x394A**
- ตัวอย่าง `COLOR_PRESSED = rgb565(150, 90, 190)` → 0x92D7, `COLOR_ACTIVE = rgb565(120, 50, 160)` (ผ่าน compile)
- ให้คะแนนเมื่อ: แก้ถูกที่ 3 ค่า, build/upload ได้, มีวิธีคำนวณ RGB565 ถูก (ไม่ต้องตรงสีตัวอย่าง)

### ข้อ 3 — ความไวของการแตะ (5 คะแนน)

- ไม่มีค่า `z` ตายตัว (ตัวเลขขึ้นกับบอร์ด ปลายนิ้ว และแรงกด ผู้สอนไม่ได้วัดชุดตัวเลขนี้) คาดหวังแนวโน้ม: แตะเบา `z` ต่ำ (เข้าใกล้ 400), กดแรง `z` สูงกว่าชัดเจน
- ตั้ง `TOUCH_Z_MIN = 700`: ต้องกดแรงขึ้นจึงรับการแตะ แตะเบาหายไป/ต้องกดหนัก (compile ผ่าน ยังไม่ได้ทดสอบบนบอร์ด)
- ตอบ: **สูงเกินไป** → ต้องกดหนัก ทำให้แตะพลาดบ่อย ; **ต่ำเกินไป** → เข้าใกล้ค่าตอนไม่แตะ (7–13) เสี่ยงแตะหลอกจากสัญญาณรบกวนหรือฟิล์มกดทับ เกณฑ์ควรอยู่ระหว่างค่าตอนไม่แตะกับตอนแตะเบาที่ต้องการรับ

### ข้อ 4 — กดค้าง (7 คะแนน)

- `LONG_PRESS_MS = 2000` : แถบเขียวเติม 2 เท่าช้า (จับเวลาด้วยนาฬิกา ≈ 2 วินาที) ; compile ผ่าน ยังไม่ได้ทดสอบบนบอร์ด
- ตอบ: ปุ่มที่มีผลใหญ่/ย้อนยาก ต้องกดค้างเพื่อยืนยัน กันการแตะพลาดครั้งเดียว ; ยาวเกินไป → ใช้งานน่ารำคาญ ผู้ใช้คิดว่าปุ่มเสีย ; แถบเติมช่วยให้ผู้ใช้รู้ว่ากำลังนับ

### ข้อ 5 — แตะตัวเลข % เพื่อหยุดพัดลม (7 คะแนน)

จุดที่ต้องแก้ (compile ผ่านแล้ว ยังไม่ได้รันบนบอร์ด):

```cpp
// 1) enum Widget เพิ่ม FanZero
    TestPaint, TestBack, TestClear,
    FanZero
};
// 2) สี่เหลี่ยมพื้นที่แตะ (ใกล้ตัวเลข % ในหน้า FAN)
constexpr Rect FAN_ZERO_RECT = {232, 78, 80, 18};
// 3) widgetName(): case Widget::FanZero: return "FanZero";
// 4) hitTest() หน้า Fan (ต้องวางก่อน ModeAuto เพื่อตรวจก่อน)
if (contains(FAN_ZERO_RECT, x, y)) return Widget::FanZero;
// 5) onActivate()
case Widget::FanZero: manualDuty(0); break;
// 6) redrawWidget(): เพิ่ม case Widget::FanZero ในกลุ่มที่ไม่ต้องวาด (ไม่มีรูปร่างปุ่ม)
```

- เกณฑ์: เพิ่มครบทุกจุด (ลืม `widgetName`/`redrawWidget` อาจเกิด warning/ข้อผิดพลาด `switch` ไม่ครบ), กดแล้ว Serial `target=FanZero`, `[FAN] manual duty = 0%`
- สังเกต: สี่เหลี่ยมนี้ต้องไม่ทับกับ `ModeAuto`/`ModeManual` ({8,34,148,40} และ {164,34,148,40} ที่ y 34–73) ; ค่าตัวอย่าง y = 78–95 ไม่ทับ แต่ต้องอยู่ก่อนแถบเลื่อน (y 96)

### ข้อ 6 — ตัวกรอง (7 คะแนน)

- `TOUCH_SMOOTH_ALPHA = 1.0` : ไม่กรอง เส้นตามนิ้วทัน แต่ขรุขระ/กระตุกได้
- `0.2` และ `TOUCH_PRESS_SAMPLES = 3` : เส้นเรียบกว่า แต่ตามนิ้วช้า (เส้นหน่วงตามหลังนิ้ว มุมถูกปัดมน) และกดลงช้าขึ้น 10 ms ; มีรายละเอียดจากโค้ด: เพราะปัดเป็นจำนวนเต็ม `lroundf(0.2 × ส่วนต่าง)` เมื่อห่างกันไม่เกิน 2 พิกเซลจะปัดเป็น 0 พิกัดจึง "ติด" ห่างจากนิ้วได้ถึง 2 พิกเซล
- แลกกับ: ความหน่วง (latency) กับความนิ่ง
- สถานะ: โค้ดค่านี้ compile ผ่าน ยังไม่ได้ทดสอบบนบอร์ด ให้ตรวจที่ "ภาพเปรียบเทียบและคำอธิบายที่สมเหตุสมผล"

### ข้อ 7 — ปัดเปลี่ยนแท็บ (10 คะแนน)

แนวทางเฉลย (compile ผ่านแล้ว ยังไม่ได้รันบนบอร์ด พฤติกรรมจริงยังไม่ยืนยัน):

```cpp
int touchStartX = 0, touchStartY = 0;   // ตัวแปรร่วม

// ใน handleTouchEvents() ตอน pressEdge (หลังได้ pressTarget):
touchStartX = touch.x;
touchStartY = touch.y;

// ตอน releaseEdge (ก่อนตรรกะคลิก):
const int dx = touch.lastX - touchStartX;
const int dy = touch.lastY - touchStartY;
const bool dragWidget = pressTarget == Widget::FanSlider || pressTarget == Widget::BlSlider ||
                        pressTarget == Widget::TestPaint;
if (!dragWidget && (page == Page::Dashboard || page == Page::Fan || page == Page::System) &&
    abs(dx) > 80 && abs(dy) < 40 && now - touch.downSince < 700) {
    const int nextPage = constrain(static_cast<int>(page) + (dx < 0 ? 1 : -1), 0, 2);  // ปัดซ้าย = แท็บถัดไป
    pressedWidget = Widget::None;
    pressTarget = Widget::None;
    if (nextPage != static_cast<int>(page)) enterPage(static_cast<Page>(nextPage));
    return;
}
```

- เกณฑ์: จำจุดกดลง, ตรวจ |dx| > 80, |dy| < 40, เวลา < 700 ms, ไม่ทำงานกับแถบเลื่อน/TOUCH TEST/หน้า calibrate, ไม่ทำให้ปุ่มเดิมถูกคลิกซ้ำ (ต้องล้าง `pressTarget` ก่อน return), ขอบเขตหน้า 0–2 (ไม่วนรอบ)
- ข้อควรสังเกต: ลำดับหน้าตามค่า enum `Page` (Dashboard = 0, Fan = 1, System = 2) ; ถ้านักเรียนใช้ค่าอื่น/ลำดับอื่นต้องอธิบายให้ถูก ให้คะแนนเต็มเมื่อโครงสร้างถูกแม้ค่าเกณฑ์ต่าง

### ข้อ 8 (โบนัส) — ใช้ขา IRQ (+10)

- **ไม่มีเฉลยที่ทดสอบ** (ผู้สอนไม่ได้ทดลองใช้ GPIO36 กับบอร์ดนี้) ตัดสินจากเหตุผลและผลที่นักเรียนสังเกต
- แนวทางที่ถูกต้องเชิงหลักการ: `pinMode(36, INPUT)` (GPIO36 เป็นขา input-only ไม่มี pull-up ภายใน) ; ถ้า IRQ = LOW อ่านชิปเต็มรอบ ถ้า HIGH ถือว่าไม่แตะและข้ามการอ่าน ; ต้องระวังว่าระหว่างอ่านชิปด้วยคำสั่งที่ไม่ใช้โหมดพัก IRQ อาจเปลี่ยนสถานะ และต้องทดลองว่าขานี้เสถียรบนบอร์ด (เคลมที่ไม่ได้ทดลอง ให้ตัดคะแนน)
- ให้คะแนนโบนัสเมื่อมีโค้ดที่ build ได้, ผลสังเกตจริงจากบอร์ด (เช่น z ขณะไม่แตะ, ความถี่การอ่าน) และอธิบายข้อจำกัดอย่างตรงไปตรงมา

## เฉลยคำถามทบทวน

1. ต่างกัน: resistive ใช้แผ่นสองชั้นกดแตะกัน, ต้องกดแรง, ใช้อะไรแตะก็ได้ (ปากกา/เล็บ/ถุงมือ), แตะได้จุดเดียว, ราคาถูก ; capacitive วัดความจุไฟฟ้า, แตะเบา, ต้องใช้ตัวนำ, หลายนิ้วได้, ไวและแม่นกว่า
2. `z = Z1 + 4095 − Z2` เทียบกับ `TOUCH_Z_MIN` = 400 เพื่อตัดสินว่ามีการแตะหรือไม่ (ไม่แตะค่าต่ำมาก ≈ 7–13 บนบอร์ดต้นแบบ)
3. ตัดค่าที่เพี้ยนครั้งเดียวจากสัญญาณรบกวน เฉลี่ยเฉพาะสองค่าที่ใกล้กัน
4. ค่าดิบ (0–4095) ไม่ตรงกับพิกเซล และขึ้นกับชิ้นส่วนแต่ละตัว ; `b = ช่วงพิกเซล ÷ ช่วงค่าดิบ`, `a = ตำแหน่งเริ่ม − b × ค่าดิบเริ่ม` หาจากเป้า 4 มุม
5. ความต้านทานของแผ่นฟิล์ม การประกอบจอ ตำแหน่ง/แรง/ปลายนิ้วที่แตะเป้าแต่ละครั้งต่างกัน (บอร์ดต้นแบบสองครั้งต่างกันราว 6–10 พิกเซล)
6. Debounce = กันสัญญาณรบกวนโดยต้องเห็นสถานะเดิมต่อเนื่องหลายตัวอย่างก่อนเปลี่ยนสถานะ ; กดลง 2 ตัวอย่าง (≈ 20 ms), ปล่อย 3 ตัวอย่าง (≈ 30 ms)
7. ผู้ใช้เปลี่ยนใจได้โดยเลื่อนนิ้วออกนอกปุ่มก่อนปล่อย, กันการแตะพลาดจากนิ้วลื่น/เหลื่อม และให้ผลตอบสนอง (สีปุ่ม) ก่อนเกิดการกระทำ
8. RECALIBRATE ทำให้ต้อง calibrate ใหม่ซึ่งรบกวนผู้ใช้ จึงต้องกดค้าง 1 วินาทีเพื่อยืนยัน ; auto-repeat: ทำ 1 ครั้งทันที, ถ้ากดค้างเกิน 500 ms ทำซ้ำทุก 150 ms
9. เขียน flash ถี่ ๆ สิ้นเปลืองรอบการเขียนและทำให้ UI ช้า ; ความสว่างจึงบันทึกตอนปล่อยนิ้วครั้งเดียวต่อการปรับ ; เกณฑ์พัดลมเป็นค่าชั่วคราว ไม่บันทึก (ออกแบบไว้)
10. 0% จอมืดสนิท มองไม่เห็นปุ่มจนปรับกลับไม่ได้ ; ไม่รวม SD เพราะ SD (Lab 8) และจอสัมผัส (Lab 9) ต้องการ SPI ชุด VSPI ซึ่ง ESP32 ชุดที่เหลืออยู่ชุดเดียว (จอ TFT ใช้ HSPI อยู่แล้ว)
